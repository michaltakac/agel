# State of the Art in JIT Compilation, and What Applies to Agel

Agel's constraints are unusual for JIT research: a tiny closed IR (const/local/builtin/fn/if/begin/call/tail-call), integers-and-tagged-values only for the in-OS backend, no heap/GC in that backend, a hard call-depth limit of 256, deterministic fuel-metered execution, no tail-call elimination in the host evaluator, and a target of running the JIT itself *inside* a tiny OS in QEMU/TCG. Nearly all JIT literature optimizes for the opposite: unbounded dynamism, best-effort throughput, non-deterministic timing, and megabytes of supporting infrastructure. The interesting question isn't "which JIT is fastest" but "which JIT *ideas* survive being starved of GC, threads, floating scheduling, and non-determinism."

## Meta-tracing (RPython/PyPy, LuaJIT)

A meta-tracing JIT (RPython, used by PyPy) doesn't compile the target language directly — it traces the *interpreter* that runs the target language, using programmer annotations to mark loop back-edges and "hot" points. When the interpreter's own back-edge counter trips a threshold, the meta-tracer records concrete execution as a linear trace through the interpreter's bytecode dispatch, then compiles that trace to machine code, guarded by the type/shape assumptions it observed. One interpreter definition yields a JIT "for free" ([Bolz & Tratt, "The Impact of Meta-Tracing on VM Design"](https://tratt.net/laurie/research/pubs/html/bolz_tratt__the_impact_of_metatracing_on_vm_design_and_implementation/); [Bolz et al., "Tracing the Meta-Level"](https://dl.acm.org/doi/10.1145/1565824.1565827)). LuaJIT is a *direct* (non-meta) tracing JIT: it traces the target program itself, using loops and calls as trace anchors, inlining all control flow into a linear SSA trace ([luajit.org](https://luajit.org/luajit.html)).

**What it buys:** a single, relatively small interpreter definition produces a competitive JIT without writing a second compiler; traces are naturally specialized to the exact types/shapes seen, giving excellent throughput on hot numeric loops.

**What it costs:** RPython is a large, idiosyncratic translation toolchain (its own restricted-Python-to-C compiler) — PyPy's build is famously slow and RAM-hungry, and the whole apparatus is thousands of lines. Traces are unpredictable in *when* they trigger and in generated-code size; trace-tree explosion and "trace bombing" from megamorphic call sites are known pathologies. Guard failures cause bailouts back to the interpreter with non-trivial reconstruction cost. None of this is deterministic across runs unless you freeze thresholds and disable all wall-clock-based heuristics.

**Fit for Agel:** poor as a direct model. Building an RPython-equivalent translation toolchain is out of proportion to Agel's IR size, and tracing's "compile whatever the profiler saw" behavior is in tension with per-form transactional, replayable execution. The *idea* worth keeping is much narrower: specialize hot code using concrete runtime shapes — but Agel can get that far more cheaply via its own tiny AOT backend and closed IR, without a meta-tracer.

## Partial evaluation / Truffle-Graal (self-optimizing AST interpreters)

Truffle interpreters are plain AST-walking interpreters whose nodes are allowed to *rewrite themselves* in place as they learn concrete types ("self-optimization" — a node that has only ever seen integers rewrites itself to an int-specialized node, falling back to a generic node on a type change). Graal then applies partial evaluation to the (currently-specialized) AST: it inlines the interpreter's own dispatch code for each node into one compilation unit and compiles the whole thing, effectively compiling the *interpreter's execution of this particular program shape* into a single optimized function ([Truffle overview](https://ssw.jku.at/Research/Projects/JVM/Truffle.html); ECOOP 2015, [tracing vs. partial evaluation](https://2015.ecoop.org/details/Truffle-2015-papers/1/Which-Meta-Compilation-Approach-is-Better-for-Self-Optimizing-Interpreters-Tracing-o)).

**What it buys:** language implementers write *only* an interpreter (plus specialization rules); Graal produces near-peak native code without a hand-written backend per language. Truffle has been used for JS, Python, Ruby, R, and more on GraalVM.

**What it costs:** it depends on the Graal compiler (itself written in Java, running on a JVM, doing partial evaluation of Java bytecode) — a huge dependency graph unsuitable for `no_std`/tiny-OS use. Node self-rewriting means the interpreter's shape is mutable and history-dependent; getting *reproducible* compiled code across two runs that saw events in different orders requires care Truffle doesn't prioritize. Compile latency for first-tier partial evaluation is high compared to a template/baseline JIT.

**Fit for Agel:** the mechanism (Graal, partial evaluation of a JVM interpreter) is completely inapplicable inside a `no_std` kernel process. But the *design pattern* — profile concrete shapes, then compile a specialized version, with an unspecialized fallback — is exactly the pattern a future tier-2 for Agel's in-OS backend could use for its (currently monomorphic, integer-only) subset: e.g., specializing arithmetic on the known tag rather than checking tags at every op, as long as the specialization is derived from *static* information already present in the closed IR (arity, known builtin) rather than from a runtime profile whose order affects output.

## Tiered JITs: V8 and JavaScriptCore

V8 runs four tiers: Ignition (bytecode interpreter that also gathers type feedback) → Sparkplug (a template/baseline JIT, "compile now, ~2x") → Maglev (a real but fast optimizing compiler, "~5x") → TurboFan (the peak optimizer, "~10x+", also handles deopt) ([v8.dev/blog/maglev](https://v8.dev/blog/maglev); [Sujeet Jaiswal's V8 write-up](https://sujeet.pro/articles/v8-engine-architecture)). JavaScriptCore mirrors this with LLInt (low-level bytecode interpreter) → Baseline (template JIT, one code snippet per bytecode) → DFG (SSA-ish, throughput-oriented, promotes after ~60 calls or ~1000 loop iterations) → FTL (multiple lowering IRs: DFG IR → DFG SSA → B3 → Air, "Faster Than Light", for code executed tens of thousands of times) ([WebKit FTL announcement](https://webkit.org/blog/3362/introducing-the-webkit-ftl-jit/); [JSC internals series](https://zon8.re/posts/jsc-internals-part2-the-llint-and-baseline-jit/)).

**What it buys:** tiering solves the "compilation cliff" — you get instant startup (interpreter), a fast floor (baseline), and asymptotically good throughput (optimizing tier) without ever blocking on a slow compile for code that only runs once. Each tier's cost is proportional to how much you've already learned is worth spending on that code.

**What it costs:** four code generators to build, test, and keep semantically identical (a notorious source of JS-engine security bugs is a mismatch between tiers). Promotion decisions rely on call/loop counters, i.e. wall-clock/PC-sampled heuristics — the opposite of deterministic. Deoptimization/OSR machinery (below) is required to move code *down* a tier when speculation fails, and *up* mid-loop.

**Fit for Agel:** the *shape* of tiering is the single most transferable idea, but Agel should use a much shallower ladder and swap "call-count heuristics" for "static, fuel-visible triggers." Concretely: (0) tree-walking evaluator (already exists, agel-core) → (1) agel-jit on the host (Cranelift, already exists) → (2) the in-OS Agel-written backend for the closed integer IR (already exists, ~250 lines). A V8/JSC-style Maglev-class middle tier is not currently justified: Agel's programs are small, fuel-bounded, and the honest bottleneck today is coverage of the IR, not throughput of a hot loop.

## Baseline/template JITs and copy-and-patch

A template (baseline) JIT precompiles one machine-code "template" per bytecode/IR op ahead of time and, at JIT time, just concatenates templates and patches in the operand-specific bits (addresses, immediates, register assignments) — no real code generation, no register allocator, no optimization passes. Xu & Kjolstad's *copy-and-patch* (OOPSLA 2021) formalizes and generalizes this: templates ("stencils") are produced automatically by compiling a generic C++ template function with an ordinary offline compiler (LLVM) once, per opcode, ahead of time; stencils have "holes" that are filled by copying bytes and writing immediates at code-gen time — no runtime dependency on LLVM at all ([copy-and-patch paper](https://dl.acm.org/doi/10.1145/3485513), [arXiv](https://arxiv.org/abs/2011.13127)). CPython adopted exactly this for its 3.13+ "JIT" — it compiles bytecode-handler C templates with LLVM at *CPython build time*, extracts the machine code for each micro-op from the resulting object files, and glues instances of them together at *interpretation time* with no LLVM present at runtime ([LWN: "Adding a JIT compiler to CPython"](https://lwn.net/Articles/977855/); [Real Python on 3.13's JIT](https://realpython.com/python313-free-threading-jit/)).

**What it buys:** compilation is reduced to `memcpy` + fixups — microsecond-scale, so it's viable even for code that only runs once or twice, with no dependency on a big code-generation library at runtime. Code quality sits between "naive interpreter dispatch" and "optimizing JIT": in CPython's case it delivered a modest (single-digit-percent) but real win, at very low implementation risk.

**What it costs:** you need an offline step (build-time, using an existing compiler) to produce the stencil library — CPython's is ~1000 lines of Python tooling plus ~100 lines of C, and depends on LLVM *at build time only*. Stencils are per-target-architecture object files; adding a new CPU/ABI means regenerating stencils for it. Code quality is capped by what the stencil author anticipated — there is no cross-op optimization, register allocation is typically fixed/spill-heavy, and specializing for a new case means writing (and re-generating) a new stencil.

**Fit for Agel: excellent, and directly buildable.** This is the technique most compatible with "a backend written in Agel that must be simple, small, and run inside a tiny OS." Agel's in-OS x86-64 backend already assembles machine code for a closed integer IR; copy-and-patch is a natural generalization of what it likely already does informally (fixed instruction sequences per IR node with args patched in). Two refinements copy-and-patch suggests: (1) generate the stencils *offline* (on the host, in Rust/Cranelift or even hand-assembled) as a small binary blob shipped with the OS image, rather than re-deriving instruction encodings by hand for every IR node in Agel source — this turns "add an opcode" into "add a stencil + one dispatch entry," and (2) keep holes limited to immediates/local offsets so patching stays `memcpy`-simple and deterministic (same bytes in, same bytes out, no host-timing dependence).

## Cranelift, and WebAssembly engines as an alternative target

Cranelift is a from-scratch, Rust-native code generator built to be simple, fast-to-compile-with, and secure, deliberately trading peak code quality for an order-of-magnitude faster codegen than LLVM; it takes CLIF (its own SSA-based target-independent IR) and lowers to x86-64/AArch64/s390x/RISC-V64 ([cranelift.dev](https://cranelift.dev/), [LWN](https://lwn.net/Articles/964735/)). It was designed as Wasmtime's JIT backend but is usable standalone (agel-jit already does this). WebAssembly engines split into interpreters (Wasm3 — minimal footprint, no JIT/AOT, good for constrained devices; wazero — pure-Go, zero platform deps) and compilers (Wasmtime — JIT/AOT only, no interpreter) ([awesome-wasm-runtimes](https://github.com/appcypher/awesome-wasm-runtimes); [WebAssembly runtime survey](https://dl.acm.org/doi/full/10.1145/3714465)). Benchmarks show the classic ~10x gap between a good interpreter (Wasm3) and a tracing/optimizing JIT (V8 TurboFan) holds up in practice ([00f.net WASM benchmark 2023](https://00f.net/2023/01/04/webassembly-benchmark-2023/)).

**What it buys (Cranelift):** already validated for Agel via agel-jit — fast, deterministic-enough compiles, no LLVM dependency, reasonable code quality for straight-line integer/control-flow code. **What it costs:** Cranelift itself is tens of thousands of lines of Rust; it cannot run *inside* the Agel OS (it needs `std`, a real allocator, and is not written in Agel), so it stays confined to the host-side agel-jit and is irrelevant to the in-OS backend's self-hosting goal.

**What Wasm engines buy as an alternative *target*:** compiling Agel's IR to WebAssembly instead of to raw x86-64 machine code would give portability (any Wasm host) and a pre-existing sandboxing/gas-metering ecosystem to borrow from. **What it costs:** it adds an entire target ISA-in-a-format to reason about, plus a Wasm engine as a runtime dependency — the OS would need a Wasm interpreter or runtime *written in Agel* to stay self-hosted, which is strictly more work than the ~250-line native backend that already exists. **Fit:** not worth pursuing now — it solves a portability problem Agel doesn't yet have (single-target x86-64 in QEMU), at the cost of an engine Agel doesn't have. Worth revisiting only if/when Agel needs to target more than one ISA or wants an external, audited sandboxing boundary.

## Inline caches / polymorphic inline caches

Inline caching remembers, at a specific call/property-access site, what shape(s) of receiver were seen last time, and rewrites the call site to a fast direct-dispatch (monomorphic) or a small linear/dictionary check (polymorphic) instead of a full generic lookup every time ([Polymorphic Inline Caches explained](https://jayconrod.com/posts/44/polymorphic-inline-caches-explained); [inline caching background](https://github.com/sq/JSIL/wiki/Optimizing-dynamic-JavaScript-with-inline-caches)). It's the single biggest lever dynamic-language JITs have for cutting the cost of "generic" operations (property get/set, method dispatch) down toward the cost of a static field access, and it degrades gracefully (falls back to the slow path, or the megamorphic case) rather than needing a hard guarantee.

**What it costs:** self-modifying call sites; cache invalidation logic when shapes change; genuinely useful only when there *is* a dynamic-dispatch cost to amortize (virtual calls, hash-map-like property lookup, hidden classes).

**Fit for Agel:** low priority today. Agel's closed IR already resolves builtins and lexical locals statically (`(builtin name)`, `(local depth slot)`) — there is no polymorphic call site to cache in the in-OS backend's integer subset; it has no dynamic property lookup, no hidden classes, no boxed heap objects. This becomes relevant only if/when the in-OS backend grows: (a) closures with variable/dynamic environments where record layout isn't known at compile time, or (b) any future generic "call this value" site that can resolve to different closures across invocations — worth flagging as a "when we add X, revisit ICs" item rather than something to build now.

## Deoptimization and On-Stack Replacement (OSR)

OSR interrupts a running frame to swap its code — either up-tier (interpreter → optimized code, mid-loop, so hot long-running loops don't have to finish once before benefiting) or down-tier (deoptimization: undo a speculative optimization whose assumption just broke, typically falling back to an unoptimized/interpreted frame reconstructed from the optimized frame's live state) ([D'Elia, "On-Stack Replacement, Distilled"](http://season-lab.github.io/papers/osr-distilled-pldi18.pdf); background from SELF, brought to the mainstream by Java JITs). It requires a precise, tier-independent mapping from "this program point in tier N" to "this program point + live-variable state in tier N±1."

**What it buys:** lets an optimizing tier help even a single very long-running loop invocation, and lets speculative optimizations (type guards, inlining assumptions) be *safely* undone rather than requiring worst-case-safe code everywhere.

**What it costs:** it is one of the most bug-prone corners of any JIT (state-reconstruction mismatches are classic security bugs in V8/JSC); it requires a stack-map / deopt-metadata format kept in lockstep with every optimization pass; mid-loop OSR entry from an interpreter into a JIT frame needs its own compiled entry stub.

**Fit for Agel: skip for now, by design.** Agel's evaluator has no tail-call elimination and a hard 256 call-depth limit — there is no "arbitrarily long-running single frame" to rescue mid-flight the way OSR rescues a hot loop in an unbounded VM; fuel budgets already bound how long any one execution can run before a transaction rolls over. The in-OS backend does whole-function ahead-of-time compilation with no speculation (it doesn't guess types — the closed integer IR has none to guess), so there is nothing to deoptimize *from*. If Agel ever adds speculative specialization (see ICs above), the right question is not "build OSR" but "can the language's small-fuel, transactional-commit semantics make it always cheaper to just recompile-and-restart from a checkpoint than to reconstruct live state in place" — likely yes, given determinism and per-form transactions already exist.

## Determinism and fuel under JIT: gas metering and replay

The nearest existing art to Agel's "fuel budget + deterministic replay" requirement is blockchain WASM metering. ewasm's model statically instruments a program with cost-counting instructions per opcode/block so that execution cost is summed deterministically regardless of which node executes it, independent of real wall-clock timing ([ewasm metering docs](https://ewasm.readthedocs.io/en/mkdocs/metering/), [Metering design](https://github.com/bnjbvr/ethereum-wasm-design/blob/master/metering.md)). The hard part is combining this with a JIT rather than an interpreter: DTVM's "DeTerministic Virtual Machine" reports that it integrates gas metering directly into JIT-compiled code by reserving a dedicated physical register (e.g. `rbx` on x86-64, `x22` on ARM64) purely to track remaining gas, decremented inline as compiled code runs, keeping metering overhead low while remaining exact and deterministic across compiler optimization levels ([DTVM paper](https://arxiv.org/pdf/2504.16552)).

**What it buys:** deterministic cost accounting *survives* compilation — the same program charges the same gas whether interpreted or JIT-compiled, which is the property Agel needs for fuel to remain meaningful once a backend (host JIT or in-OS backend) is involved instead of the tree-walker.

**What it costs:** every code-generation path (including any future optimizing tier) must be taught to emit metering instructions consistently, and any instruction reordering/fusion optimization must not change total accounted cost, which constrains which optimizations are safe.

**Fit for Agel: directly applicable, and should be adopted as policy now, before more tiers are added.** Concretely: (1) reserve a register (or a fixed memory cell, given the current backend is register-poor by design) in the in-OS backend's calling convention for remaining fuel, decremented by a static, per-IR-node cost baked into each stencil/emission — this is a natural marriage with the copy-and-patch idea above, since a stencil can simply include its own fixed fuel-decrement instruction; (2) treat "fuel accounting is part of the opcode's stencil, not a separate pass" as an invariant so no future optimization can accidentally elide it; (3) verify by cross-checking fuel consumed by the tree-walking evaluator against fuel consumed by compiled code on the same program as a conformance test — cheap, and catches drift immediately.

## Metacircular JIT compilers: what made the bootstrap work

Four data points on JITs/VMs written in the language they run, and what let each one actually bootstrap:

- **Jikes RVM** (JVM written in Java): has no interpreter at all — every method is compiled (lazily, by a fast non-optimizing "baseline" compiler on first call) before it ever runs. Bootstrapping works via a *boot image*: a snapshot of the Java object graph the VM needs, built by reflection from a separate *host* JVM, loaded at startup by a small C loader that then transfers control into native VM code ([Jikes RVM overview](https://www.jikesrvm.org/), [Beautiful Architecture ch. 10](https://www.oreilly.com/library/view/beautiful-architecture/9780596155780/ch10.html)). The key trick: you don't need Jikes RVM to compile Jikes RVM — you need *some* JVM to produce the frozen initial heap image, after which the produced binary is self-sufficient.
- **Maxine VM** (~95% Java, ~5% C glue): same boot-image strategy; Graal itself grew directly out of Maxine's compiler work ([Maxine overview](https://en.wikipedia.org/wiki/Maxine_Virtual_Machine)). The lesson repeats: metacircularity is about the *steady state*, not the cold start — a non-circular bootstrap step (image-building on a host) is normal and accepted.
- **PyPy/RPython**: RPython (a restricted, statically-typeable subset of Python) is translated to C by a Python interpreter running the translation toolchain — "a snake swallowing itself." The bootstrap is expensive (PyPy's own build is slow and RAM-hungry) but only needs to happen once per RPython-toolchain version, not per user program ([PyPy architecture docs](https://doc.pypy.org/architecture.html)).
- **Squeak/Cog/Sista** (Smalltalk VM written in Smalltalk): VMMaker lets the VM (interpreter, and the Cog JIT) be developed and *simulated* live inside a running Smalltalk image, then mechanically translated (a restricted, C-like fragment of Smalltalk) to C for the production VM binary — the same "restricted subset + translator" pattern as RPython, but older and lighter-weight ([wiki.squeak.org VM overview](https://wiki.squeak.org/squeak/676)).
- **Chez Scheme's nanopass framework**: not metacircular in the VM sense, but relevant as "self-hosting done right" — the compiler is organized as many small, independently-checkable passes (a nanopass compiler), reducing each pass to something nearly provably correct; bootstrapping onto a new platform is solved by keeping a portable-bytecode ("pb") backend that runs anywhere, used to get a first foothold before native-code backends are built for that target ([ChezScheme IMPLEMENTATION.md](https://github.com/cisco/ChezScheme/blob/main/IMPLEMENTATION.md)).

**Common thread, and its relevance to Agel:** every real metacircular system accepts a *non-circular* first stage (a host compiler, a frozen boot image, a portable-bytecode fallback) rather than trying to be self-sufficient from instruction one. Agel is already following this pattern correctly: the Rust host (agel-core, agel-jit) is the "host JVM" that builds and runs the Agel-written x86-64 backend; the honest goal is not eliminating Rust but shrinking its share over time, exactly as Maxine reduced its C sliver to ~5%. The nanopass lesson (small, checkable passes; a portable fallback) is the most directly transferable piece: as the Agel-written backend grows past "assemble one closed integer IR," structuring it as small composable lowering passes (rather than one monolithic emit function) will keep it auditable at ~250-line-module scale rather than accreting into an unreadable one-shot compiler.

## Recommendations for Agel

1. **Do not build a tracing/meta-tracing JIT.** The infrastructure cost (an RPython-scale translation toolchain, or hand-written trace recording/guards/bailout) is wildly disproportionate to Agel's closed IR, and non-deterministic hot-path detection fights the project's determinism/replay goals directly.
2. **Adopt copy-and-patch as the concrete mechanism for the in-OS Agel-written backend.** Generate per-IR-node machine-code stencils offline (on the host, via Cranelift or a small hand-written assembler) as a static blob shipped with the OS; have the Agel-written backend's job be reduced to "select stencil, copy bytes, patch holes (immediates, local slot offsets, jump targets)." This is the single highest-leverage change: it turns "add an IR node to the backend" into "add one stencil," keeps the backend's own source small (in the spirit of its current ~250 lines), and keeps codegen a deterministic `memcpy`+fixup with no floating heuristics.
3. **Bake fuel accounting into each stencil now, as an invariant, not an add-on pass.** Follow DTVM's register-reserved-for-gas pattern: pick one register or fixed slot in the backend's calling convention for remaining fuel, and have every stencil include its own fixed decrement. Add a conformance test comparing fuel consumed by the tree-walker vs. the compiled path on the same programs, so drift is caught immediately rather than discovered as a correctness bug.
4. **Keep the tier ladder shallow and static-trigger, not counter/heuristic-driven.** The three tiers that exist (tree-walker → host Cranelift JIT → in-OS backend) are enough; don't add a V8/JSC-style middle "fast-but-not-peak" tier until there's a concrete workload that needs it. If/when a middle tier is wanted, prefer a threshold that is part of the deterministic program (e.g., "compile any function called more than N times within this world's transaction," where N and the counter are part of replayable state) over wall-clock/PC-sample-based promotion.
5. **Treat inline caches and OSR/deoptimization as "not yet, and maybe never."** Both only pay for themselves once the backend has genuine dynamic dispatch or speculative type assumptions to amortize; today's closed integer IR has neither. Revisit inline caches specifically when/if the backend gains closures with runtime-varying call targets; when that day comes, prefer a Truffle-style "specialize from statically-known information first, runtime profile second" bias to keep results reproducible.
6. **Don't chase WebAssembly as a target** unless/until Agel needs a second ISA or an externally-audited sandbox boundary; right now it would add a whole engine-in-Agel obligation to stay self-hosted, for a portability problem (multi-ISA) Agel doesn't have yet (single target: x86-64 under QEMU/TCG).
7. **Structure the Agel-written backend as small, composable, checkable passes now, nanopass-style**, even while it's ~250 lines — it is far cheaper to keep this discipline from the start than to retrofit it once stencil selection, register/slot allocation, and fuel-instrumentation are all interleaved in one function.
8. **Keep the Rust-hosted stage explicitly as the "boot image / host JVM," not a target for elimination.** Every successful metacircular VM (Jikes RVM, Maxine, PyPy, Squeak) kept a non-circular bootstrap stage indefinitely; Agel's honest self-hosting metric should be "shrink Rust's share of the runtime surface over time" (as Maxine shrank to ~5% C), not "reach zero Rust."
9. **Next three concrete rungs, in order:** (a) offline stencil generator for the in-OS backend's current opcode set, replacing any ad hoc instruction-encoding logic; (b) fuel-register invariant + tree-walker/compiled-path fuel conformance test; (c) extend the closed IR's coverage (more builtins, richer control flow) via new stencils before considering any new compilation tier — coverage of the existing three-tier design is a better investment right now than a fourth tier.
