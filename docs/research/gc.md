# Garbage Collection: State of the Art and Alternatives, for Agel

Agel has three memory regimes that need distinct answers, not one:

1. **The hosted Rust runtime** (world = ~1 MB with stdlib, cloned per transaction as a rollback copy; agents have isolated heaps + mailboxes; failed turns roll back to a checkpoint).
2. **The in-OS process runtime**: a size-class allocator over `brk` in a 64 MiB window, no compaction, running as a userspace process inside Agel's own kernel.
3. **The native evaluator inside the kernel**: fixed memory, a copying collector that runs at commit over >4096 cells, and a 3-bank transactional world (active/previous/scratch).
4. **The new x86-64 backend written in Agel itself**: currently integer-only IR, bump-allocated closure arena, no GC — the open question is how it grows to lists/text.

Below is what the field has tried, what it costs, and where it fits (or doesn't) each of these four targets.

## Copying collectors: Cheney, semispace, and why they suit immutable data

Cheney's algorithm (1970) replaced the classic Fenichel–Yochelson recursive/pointer-reversal copying scheme with a **breadth-first, iterative, non-recursive** two-finger scan of to-space — no stack, no recursion, no per-object mark bits. It is the natural fit for languages built on immutable cons-like structures because there is no need to track intra-object mutation for most objects; you copy live data once, compact it, and bump-allocate afterward. See the original description via [Wikipedia's summary of Cheney's algorithm](https://en.wikipedia.org/wiki/Cheney%27s_algorithm) and Baker's classic ["Cheney on the M.T.A."](https://www.plover.com/~mjd/misc/hbaker-archive/CheneyMTA.html) note, which shows how to turn C's *call stack itself* into a to-space bump allocator by compiling to continuation-passing style so C functions never return — used in production by [CHICKEN Scheme](https://www.call-cc.org/) and [Cyclone Scheme](https://justinethier.github.io/cyclone/docs/Writing-the-Cyclone-Scheme-Compiler-Revised-2017). This is directly relevant to a backend compiling Agel to machine code: if the generated code is arranged so the machine stack pointer doubles as the bump pointer, you get copying GC almost for free, at the cost of committing to a CPS-style codegen discipline.

Generational hypothesis (most objects die young) motivates a **nursery + mature space** split: cheap frequent minor collections scan only the young generation via a remembered set of old→young pointers (a write barrier), with rare major collections over the whole heap. This is exactly what BEAM (Erlang) and SBCL do (below) and is the default recommendation for any managed heap with allocation-heavy, short-lived garbage — which describes almost every Lisp-like evaluator, Agel included.

## Immix, RC-Immix, LXR (Blackburn, Zhao, McKinley)

**Immix** (Blackburn & McKinley, PLDi 2008, [paper](https://users.cecs.anu.edu.au/~steveb/pubs/papers/immix-pldi-2008.pdf)) is a "mark-region" collector: memory is organized into 32 KB blocks of 128 B lines; live *lines* are marked, not individual objects, and evacuation ("opportunistic defragmentation") is optional and localized to fragmented blocks. It gets semispace-like mutator throughput and locality without semispace's 2x space tax, and sits between mark-sweep and copying in complexity. It's the workhorse plan inside MMTk, and its **StickyImmix** variant does in-place generational GC using a sticky mark bit instead of an evacuating nursery, avoiding a separate nursery space entirely ([MMTk docs](https://www.mmtk.io/status), [rust-hosted-langs book chapter](https://rust-hosted-langs.github.io/book/part-stickyimmix.html) — a good from-scratch Rust implementation walkthrough).

**LXR** (Zhao, Blackburn, McKinley, PLDI 2022, [paper](https://www.steveblackburn.org/pubs/papers/lxr-pldi-2022.pdf), [arXiv](https://arxiv.org/abs/2210.17175)) fuses reference counting and tracing: RC handles the common case with a low-overhead coalescing write barrier, remembered sets from RC let the collector copy mature objects judiciously, and concurrent tracing runs only to reclaim cycles. Reported gains are large (7.8x throughput, 10x tail latency over Shenandoah on Lucene in a tight heap) but this is a **research-grade, deeply concurrent** collector — thousands of lines of tightly-tuned Rust, designed for JVM-scale heaps and multi-core throughput. It is almost certainly overkill for Agel's ~1 MB-to-tens-of-MB worlds; the engineering cost (concurrent barriers, cyclic-GC fallback, lazy decrement processing) would dwarf the benefit at this heap size.

**Takeaway**: Immix-family ideas (line-granularity reclamation, sticky mark bits for cheap generational behavior without a copying nursery) are a reasonable *upgrade path* for the hosted runtime if clone-per-transaction ever becomes a bottleneck, but LXR-style RC+tracing hybrids are not worth the complexity at Agel's scale.

## MMTk — could a `no_std` Agel runtime bind it?

[MMTk](https://www.mmtk.io/status) ("Memory Management Toolkit") is a Rust framework of composable GC building blocks (allocators, spaces, work-packet-based parallel tracing) designed to be bound into a *host VM* via a `VMBinding` trait — the host implements object-model queries (size, references-within, scan-object) and MMTk supplies the collector plans (NoGC, MarkSweep, SemiSpace, Immix, GenImmix, StickyImmix, and experimental LXR). Official bindings exist for JikesRVM, OpenJDK, V8, Julia, Ruby (see [mmtk-core](https://github.com/mmtk/mmtk-core), [docs.rs/mmtk](https://docs.rs/mmtk/latest/mmtk/)); recent work covers [Rust for high-performance GC implementation](https://www.researchgate.net/publication/303773692_Rust_as_a_language_for_high_performance_GC_implementation) and a Julia case study ([Reconsidering GC in Julia](https://www.steveblackburn.org/pubs/papers/julia-ismm-2025.pdf)).

Binding it into Agel's kernel-hosted `no_std` native evaluator is a heavier lift than it looks: MMTk assumes OS-level services (mmap-based space reservation, threads for parallel GC work, often `std`), a multi-space heap abstraction bigger than Agel's fixed 3-bank world, and a VM binding surface (stack scanning, safepoints, object-model trait impls) that is substantial boilerplate for a payoff (parallel/concurrent tracing, defragmentation) Agel's small deterministic worlds don't need. It is a much better fit for the **hosted Rust runtime** (which already runs under `std`, could reserve real memory pages, and might eventually want a bigger, longer-lived heap than "clone the whole 1 MB world every transaction") than for the in-kernel native evaluator. Even there, adopting MMTk trades a small hand-rolled collector for a large, general dependency whose determinism/replay guarantees would need separate auditing — a nontrivial cost against Agel's "small predictable cores" value.

## Perceus / Koka / Lean 4: reference counting with reuse, and Lobster's static RC

[Perceus](https://xnning.github.io/papers/perceus.pdf) (Reinking, Xie, de Moura, Leijen; PLDI 2021; MSR tech report at [microsoft.com](https://www.microsoft.com/en-us/research/wp-content/uploads/2020/11/perceus-tr-v1.pdf)) is precise, garbage-*free* (no cycle collector — programs must be structured to avoid cycles, or cycles are handled separately) reference counting with compiler-inserted, statically-optimal inc/dec placement plus two more ideas: **reuse analysis** (in-place update: matching-then-reconstructing a data structure with refcount 1 reuses the memory instead of alloc/free) and **borrow inference** (drops redundant inc/dec pairs across a call). It ships in production in [Koka](https://koka-lang.github.io/) and in **Lean 4**, whose entire elaborator and kernel run on Perceus-managed memory competitively with hand-written C. Lobster (a hobbyist/production game-scripting language) does whole-program **compile-time reference counting**, statically eliding refcount ops where escape analysis proves single ownership — closer in spirit to Rust's own compile-time ownership than to a runtime GC.

This is highly relevant to Agel because Agel's values are already **immutable** — the single hardest problem for Perceus (safe in-place reuse under aliasing) requires exactly the same "is this the only owner" reasoning that persistent/functional data structures need for their own optimizations. If Agel's compiler (whether the tree-walking evaluator or the new Agel-in-Agel backend) can track "last use of this list/map cell" it can emit dec/reuse operations without a general GC at all for a large fraction of code — this is the strongest alternative-to-tracing-GC option for the native/compiled path, not just an academic curiosity.

## Pony's ORCA and BEAM's per-process heaps — the closest analogue to Agel's isolated agent heaps

**Pony ORCA** ([tutorial](https://tutorial.ponylang.io/appendices/garbage-collection.html), [paper](https://www.ponylang.io/media/papers/OGC.pdf), [OOPSLA'17 "Orca: GC and type system co-design for actor languages"](https://dl.acm.org/doi/10.1145/3133896)) is a fully concurrent, per-actor GC protocol using deferred, weighted distributed reference counting, requiring no synchronization beyond the actor model's own message send/receive and relying on Pony's reference-capability type system (co-designed with the GC) to make counting safe without atomics. Each actor can be collected independently and concurrently with any number of others.

**BEAM** gives each Erlang **process its own heap** and runs an **independent, per-process generational semispace Cheney collector**; a young/old-generation split promotes survivors, and message payloads sent between processes are *copied* into the receiver's heap (deferred until pattern-matched on the receive clause, since OTP 19 — see [Erlang's official GC docs](https://www.erlang.org/doc/apps/erts/garbagecollection.html) and the [BEAM Book](https://blog.stenmans.org/theBeamBook/)). Because each process's heap is small, isolated, and doesn't need to synchronize with other processes' collectors, GC pauses are *local* — one process pausing does not stop the whole system, which is the real payoff (not the algorithm, which is a bog-standard Cheney copy).

Both of these describe Agel's isolated-agent-heap architecture almost exactly. **This is the strongest structural argument in this whole report**: Agel does not need one global GC — it needs one *small, local, per-agent* GC (or arena), because the isolation boundary is already drawn at the agent, and rollback-on-failure already implies the checkpoint/copy machinery a nursery collector would want anyway. The "message copying" pattern (copy data across the mailbox boundary rather than sharing pointers) is also a clean way to keep agent heaps from developing cross-heap references that would otherwise force a global GC.

## Region-based memory management: MLKit, Cyclone

**Tofte–Talpin regions** (as implemented in the [ML Kit](https://en.wikipedia.org/wiki/Region-based_memory_management), summarized in ["A Retrospective on Region-Based Memory Management"](https://link.springer.com/article/10.1023/B:LISP.0000029446.78563.a4)) infer, at compile time, lexically-scoped regions into which allocations go, and free a whole region (O(1)) when its scope ends — no runtime tracing at all, in exchange for a static effect/region-inference type system that programmers occasionally have to fight (small program changes can drastically shift inferred lifetimes). **Cyclone** ([Grossman & Morrisett, PLDI 2002](https://www.cs.umd.edu/projects/cyclone/papers/cyclone-regions.pdf)) applies the same idea to a C-like language with explicit region pointers checked by the type system, trading GC entirely for a region-typed borrow-like discipline.

Agel's **3-bank transactional world (active/previous/scratch)** and **per-transaction rollback copy** are *already* a region scheme in miniature: a transaction is a region; commit either promotes it or discards it. This is the single biggest "free lunch" available to Agel: region deallocation is exactly what "throw away the rollback copy" already does, and it needs no type-system innovation because the transaction boundary is already a hard, explicit, dynamic scope — Agel gets the payoff of MLKit/Cyclone-style region reclamation without their static-inference cost, because the "region" boundary (an agent turn, a world transaction) is a value in the language already, not something a region-inference pass has to discover.

## Bump allocation / arenas with transaction-scoped reclamation

This is the degenerate, cheapest-possible GC: never free individually, bump-allocate, and reclaim the whole arena at once when its scope ends. It requires that nothing inside the arena needs to outlive the scope and that nothing outside the scope holds a pointer in. Agel's backend already does this for closure records in the new x86-64 IR. The open problem stated in the prompt — growing this to lists/text — is exactly the point where "arena-and-never-free" breaks down, because lists and text are exactly the values that get shared, returned, and outlive a single call frame; a pure bump arena without any reclamation would grow without bound across a long-running agent unless every value provably dies at scope exit (region inference) or the arena boundary is short-lived and hard (a whole transaction, discarded on rollback or after being flattened into a persistent world state).

## Conservative vs precise stack scanning; stack maps vs shadow stacks

A *precise* collector needs to know, at every point the collector can run (a "safepoint"), exactly which stack slots/registers hold heap references versus raw integers. Two implementation strategies:

- **Stack maps**: the compiler emits, per safepoint, a table describing which slots are live references (see [LLVM's GC documentation](https://llvm.org/docs/GarbageCollection.html) for the `gcroot`/statepoint mechanisms). Zero runtime overhead per call, but requires codegen support and binary-size overhead for the tables, and only works at points the compiler chose to emit a map for.
- **Shadow stack**: the compiler emits explicit push/pop of every live reference onto a separate stack maintained alongside (or instead of scanning) the real call stack. Simple to implement in a hand-written backend (no stack-map encoding/decoding needed), portable, but adds real per-call overhead and code size ([overview in the "Conservative vs Precise GC" piece](https://medium.com/@gtashnik11/conservative-vs-precise-gc-what-to-choose-318d069d994c)).
- **Conservative scanning** (Boehm-GC's approach, below) treats every stack word that looks like a valid heap pointer as a root, needing no compiler cooperation at all, at the cost of occasionally retaining garbage (a value that happens to alias a valid address) and being unable to move objects it can't prove are real pointers. Interestingly, [recent work shows conservative stack scanning can outperform precise scanning in practice](https://wingolog.org/archives/2024/09/07/conservative-gc-can-be-faster-than-precise-gc) (JavaScriptCore uses it; V8 has explored moving to it) once you account for the engineering and runtime cost of maintaining precise stack maps.

For Agel's new x86-64-backend-written-in-Agel, a **shadow stack is the pragmatic starting point**: it needs no object-file metadata format, no unwinder integration, and is straightforward for an Agel-emitted prologue/epilogue to maintain (push a reference when it's stored to a stack slot that must survive a call, pop it on return). Precise stack maps are the "grown-up" version to migrate to once the codegen is mature enough to track liveness per safepoint; conservative scanning is a reasonable fallback if the team wants to skip both, given Agel's small heaps make "occasionally over-retaining" cheap, but conservative scanning forbids compacting/copying that specific region unless pointers within it are also treated as ambiguous roots (Boehm-GC handles this by simply never moving objects).

## Incremental/concurrent vs deterministic pause behavior

Concurrent/incremental collectors (Baker's algorithm, LXR, most production JVM/V8 collectors) trade collector complexity (tri-color invariants, read/write barriers, careful synchronization) for shorter or hidden pauses. Agel's stated values are determinism and replay under deterministic fuel — a **stop-the-world collector triggered at a deterministic point (commit, or a fixed cell-count threshold) is strictly easier to make replay-correct** than a concurrent collector, because GC timing itself does not need to be part of the replayed trace. This matches the current design (GC "at commit" in the native evaluator) and is the right call to keep: concurrent GC buys latency, not correctness, and Agel's transactional model already bounds pause impact by scoping work to one transaction at a time.

## Memory safety guarantees

Tracing/copying collectors (Cheney, Immix) provide memory safety as a byproduct of precise root-tracking: a live object is never freed while reachable, and a moved object's old address is never read. RC (Perceus, ORCA) is safe as long as counts are correctly maintained (a bug undercounts → use-after-free; overcounts → leak, safe but wasteful) and cycles are handled or structurally excluded. Arena/region schemes (Cyclone, Agel's 3-bank world) get safety from the *type system or the runtime discipline* proving nothing outlives its region — the compiler (or a hand-checked invariant) is doing what the collector would otherwise verify dynamically, so an unsound region-lifetime assumption is a silent memory-safety bug with no collector to catch it. This matters directly for the Agel-in-Agel backend: a bump arena with "collect never" is only safe as long as the compiler can *prove* no reference to arena-allocated data escapes the arena's lifetime; once lists/text are added and can be returned from a function or stored in a longer-lived closure, that proof obligation becomes real and either needs a tracing collector, a region-typed escape check, or Perceus-style precise ownership tracking.

## Historical Lisp/Smalltalk approaches worth remembering

- **Symbolics Lisp Machines** used Baker's incremental copying collector in hardware/microcode on the 3600 — semispace evacuation, "ephemeral objects" (a generational-like fast path for very young objects), tagged architecture with hardware assists for the write barrier ([Moon, "Garbage Collection in a Large Lisp System", 1984](https://dl.acm.org/doi/pdf/10.1145/800055.802040); [background on hardware-assisted GC](https://en.wikipedia.org/wiki/Hardware-assisted_garbage_collection)). The lesson for Agel: incremental copying is old and well-understood; the "ephemeral"/generational split long predates modern generational GC terminology.
- **Smalltalk-80's Deutsch–Bobrow deferred reference counting** ([Deutsch & Schiffman, POPL 1984](https://dl.acm.org/doi/10.1145/800017.800542)) ignored refcount updates from stack/register references (the highest-churn source) and periodically reconciled a "zero count table" against a stack scan — eliminating ~85% of refcounting operations. This is a precursor to Perceus's borrow inference: both attack the same problem (stack-local refcount churn) by different means (runtime deferral vs. static analysis).
- **Self/Strongtalk** pioneered fast generational GC with write barriers and remembered sets tuned for a highly dynamic, message-heavy language ([Self bibliography on write barriers](https://bibliography.selflanguage.org/write-barrier.html)); **Squeak's Spur** object format/GC replaced Squeak's older pointer-reversing mark-compact collector with a generation scavenger ([Cog blog on Spur](http://www.mirandabanda.org/cogblog/2013/09/05/a-spur-gear-for-cog/)).
- **SBCL's gencgc** is "a Cheney GC with generations bolted on," using page-granularity hardware write-barriers (mprotect-based) for the remembered set ([Cracauer on SBCL's gencgc](https://medium.com/@MartinCracauer/llvms-garbage-collection-facilities-and-sbcl-s-generational-gc-a13eedfb1b31)) — illustrative of how much engineering complexity a generational collector accrues once you add hardware write-barriers and page-based bookkeeping, versus a from-scratch software write barrier.
- **Boehm-Demers-Weiser (BDWGC)** ([hboehm.info/gc](https://www.hboehm.info/gc/), [GitHub](https://github.com/bdwgc/bdwgc)) is the standard "bolt GC onto an unmanaged language" answer: conservative stack/register scanning, mark-sweep, works as a drop-in malloc replacement, optional incremental mode. It's the lowest-effort way to add automatic memory management to a C/Rust `unsafe` runtime, at the cost of retaining some false positives and being unable to compact.
- **"GC written in the language itself"**: Jikes RVM is a Java VM written in Java (meta-circular), and MMTk itself is written in Java for it, relying on aggressive JIT inlining to get C-like performance from Java-in-Java GC code ([JikesRVM related work](https://www.jikesrvm.org/Resources/RelatedWork/), [arXiv survey](https://arxiv.org/abs/1601.02536)). **Squeak's VM** is written in **Slang**, a restricted Smalltalk subset mechanically translated to C ([Squeak development docs](https://squeak.org/development/), [transpiling Slang paper](https://www.hpi.uni-potsdam.de/hirschfeld/publications/media/BraunTaeumelMirandaHirschfeld_2023_TranspilingSlangMethodsToCFunctionsAnExampleOfStaticPolymorphismForSmalltalkVmObjects_AcmDL.pdf)) — this is the closest historical precedent to "Agel-written runtime code:" a disciplined, restricted subset of the high-level language that a translator lowers to native code, used specifically so the GC and interpreter can be written in the language they implement. **Klein** ([GitHub](https://github.com/AdamSpitz/klein), [Self blog](https://blog.selflanguage.org/tag/klein/)) pushed further — a Self VM written entirely in Self, metacircular, live-editable — but notably **never fully self-hosted its own GC**, which is a useful cautionary data point: self-hosting the collector specifically (as opposed to the interpreter/compiler) is where these projects historically stalled. **Maxine** is a more modern (Oracle Labs) meta-circular JVM-in-Java in the same lineage ([Wikipedia](https://en.wikipedia.org/wiki/Maxine_Virtual_Machine)).

## Recommendations for Agel

**1. Heap design for Agel-emitted machine code.** Use a **per-agent (and per-world-transaction) Cheney semispace**, not Immix, as the first real GC for the x86-64 backend: it is the simplest correct copying collector, needs no line/block bookkeeping, and its "stop, flip, scan-and-copy breadth-first" structure matches Agel's existing "GC at commit" mental model in the kernel's native evaluator. Root discovery should start as a **shadow stack**: have the Agel-in-Agel codegen emit explicit push/pop of any register or stack slot holding a heap reference across a call or a potential allocation point, rather than building precise stack-map tables (that's a later optimization once the compiler has real liveness analysis). Migrate to precise stack maps only if shadow-stack overhead shows up as a real cost; don't build conservative scanning at all, since Agel controls 100% of the codegen and has no interop boundary with unmanaged code that would need it. Rough complexity estimate: a from-scratch semispace collector plus bump allocator plus shadow-stack root walking, written in Agel, is on the order of **300-600 lines** for the collector core (allocate/copy/forward-pointer/flip) plus **100-200 lines** of codegen changes to emit shadow-stack pushes/pops at call sites and allocation sites — comparable in scope to the rust-hosted-langs book's [Sticky Immix walkthrough](https://rust-hosted-langs.github.io/book/part-stickyimmix.html), which is a good line-by-line model to adapt (though Agel should start simpler than Sticky Immix's line-marking).

**2. Should the hosted Rust runtime move off clone-per-transaction?** Not urgently, but yes as the next optimization once world sizes grow past the current ~1 MB. The cheapest win with the least new machinery is switching the world's internal collections (the assoc-vec maps, the Vec-backed lists) to **persistent, structurally-shared data structures** (e.g. `rpds` or `im`, both already exist as off-the-shelf crates — [rpds](https://github.com/orium/rpds), [im](https://docs.rs/im)) so that "clone the world" becomes O(1) pointer/Arc-count bump rather than O(size); this preserves Agel's existing "clone freely" mental model exactly, just makes the clone cheap. Perceus-style reuse (in-place update when a transaction's rollback copy's refcount hits 1, i.e. no one else is holding the old snapshot) is a further, second-order optimization worth deferring — it needs static "am I the only owner" reasoning that the interpreter doesn't currently do, and the win only matters once persistent-structure clone overhead itself becomes measurable. Cost: swapping in `rpds`/`im` for the world's map/vector types is a moderate, mostly mechanical refactor (touches every place the world's collections are read/written, but not the transaction/rollback logic itself) — likely a few days to a couple of weeks depending on how cleanly the current data model is factored; adopting Perceus-style reuse would be a much larger, multi-week research-grade effort and shouldn't be scheduled until the simpler win is exhausted.

**3. Using the transactional/rollback model to make GC simpler.** This is Agel's biggest structural advantage and should be leaned on hard: treat **each transaction as a region** (à la MLKit/Cyclone) and **each agent turn as an arena** (à la BEAM/Pony-ORCA's per-actor heaps). Concretely: allocate turn-scoped garbage into a bump arena that is simply discarded on rollback (no tracing needed at all for the rollback path — this is "GC" for free) and only run the real collector (Cheney semispace) over what's left after a successful commit, i.e., collect *survivors*, not everything. Because agent heaps are isolated and mailboxes copy data across the boundary (as BEAM does), a per-agent collector never needs to trace into another agent's heap — this keeps each collection small and bounded, and keeps a bug in one agent's GC from corrupting another's. This also means Agel does not need one "big" GC ever; it needs N small, independent ones, which is both simpler to implement and easier to reason about for determinism/replay.

**4. Is MMTk (or another crate) worth binding for the host?** Not yet. MMTk is the right *reference design* to study (Immix/StickyImmix plan, VMBinding trait shape) but binding it into the hosted Rust runtime today would import a large, `std`-oriented, multi-space GC framework to manage a ~1 MB-to-low-tens-of-MB heap that a simpler persistent-data-structure refactor (recommendation 2) already solves more cheaply. Revisit MMTk only if/when the hosted runtime's world sizes grow into the range (tens to hundreds of MB, many concurrent long-lived worlds) where its parallel/concurrent tracing plans would pay for their integration cost; even then, prefer binding it at the **hosted Rust runtime** layer only, never inside the `no_std` kernel evaluator, where its OS-service assumptions (mmap, threads) don't hold.

**5. Next three rungs.** (a) Ship the **shadow-stack + Cheney semispace** for the x86-64 backend as the minimum viable GC that unblocks lists/text in Agel-emitted code — this is the prerequisite for the backend to stop being integer-only. (b) Refactor the hosted runtime's world representation onto `rpds`/`im`-style persistent structures so "clone per transaction" becomes cheap structural sharing instead of a real copy, buying headroom before any heavier GC work is needed. (c) Formalize the **region-per-transaction, arena-per-agent-turn** discipline explicitly in the runtime's design docs and tests (including a "does rollback actually free the arena" test and a "does an agent's GC ever trace into another agent's heap" invariant check), so the isolation-based GC simplification in recommendation 3 is a documented guarantee, not an emergent accident — this is cheap to do now and becomes much more valuable once more contributors (or Agel-written code) touch the runtime.
