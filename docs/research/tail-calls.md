# Tail-call elimination and control-flow implementation for Agel

## 1. Why this matters for Agel specifically

Agel has two places where "no proper tail calls" bites:

- **(A) `agel-core`**, the `no_std`-capable Rust tree-walking evaluator that runs *inside* the Agel OS as a process with a fixed 4 MiB stack, a call-depth budget of 256, and deterministic fuel. Every top-level form is transactional (commit/rollback), and agent turns roll back on failure. A 1000-iteration explicit-self loop like `(fn (self n acc) (if (= n 0) acc (self self (- n 1) (+ acc n))))` currently blows the 256-depth budget with `resource/call-depth`, even though semantically it is one loop.
- **(B) The Agel-written x86-64 backend**, a compiler-in-the-language that lowers a closed IR with explicit `(tail-call f args)` nodes through Cranelift for JIT, and separately hand-emits x86-64 (rbp-based frames, static link under rbp, caller pushes closure+args, caller pops) for AOT/self-hosting. Today a `(tail-call ...)` node is compiled as an ordinary `call` + `ret`, so it still grows the native stack — the IR *distinguishes* tail position but the codegen doesn't yet *exploit* it.

Both problems are well-trodden ground in the Scheme/Smalltalk/Erlang/Rust/Wasm world. Below is what's out there, and what's cheapest to adopt at each level.

## 2. The R7RS requirement and why it forces implementation choices

R5RS/R7RS do not merely suggest TCO as an optimization — they define a call as "active" if it may still return, and require an implementation to support "an unbounded number of active tail calls" using *no additional space* per tail call ([R7RS §3.5, "proper tail recursion"](https://small.r7rs.org/attachment/r7rs.pdf); summary at [people.csail.mit.edu/jaffer/r5rs/Proper-tail-recursion.html](https://people.csail.mit.edu/jaffer/r5rs/Proper-tail-recursion.html)). Will Clinger's paper "Proper Tail Recursion and Space Efficiency" ([PDF](https://www.cs.tufts.edu/~nr/cs257/archive/will-clinger/proper-tail-space.pdf)) is the classic formal treatment: it defines *asymptotic space complexity* for programs with tail calls and shows why a correct Scheme implementation cannot just "optimize when convenient" — the space bound is part of the language semantics, observable by programs that loop forever without growing memory. This framing is useful for Agel: if tail calls are to be a real guarantee (not a best-effort optimization the fuel/depth budget can silently defeat), the depth accounting needs to *know* which calls are tail calls, the same way Scheme's semantics does.

## 3. Classic interpreter techniques for tail calls

### 3.1 Trampolining
The simplest fix for a tree-walking interpreter with no target-language TCO (true of the JVM, true of Rust without `become`). Instead of `eval` calling itself recursively for a tail position, it returns a *thunk* describing "call this function with these args," and an outer trampoline loop keeps invoking thunks until a final value appears. See Eli Bendersky's writeup ["On Recursion, Continuations and Trampolines"](https://eli.thegreenplace.net/2017/on-recursion-continuations-and-trampolines/) and the Java-focused ["Trampoline Pattern in Java"](https://java-design-patterns.com/patterns/trampoline/) (used because "common JVM implementations do not natively support TCO"). Trampolines convert stack depth into heap-allocated thunks/loop iterations — a real fix, at the cost of allocating a small "next step" value per tail call and restructuring `eval`'s recursion into an explicit loop.

### 3.2 CPS conversion
Convert the whole interpreter (or the compiled program) into continuation-passing style so that no function ever needs to return to its caller — every call is by construction the last thing done, and calls are just "tail calls" all the way down. This is how CHICKEN Scheme compiles to C: transform to CPS, generate C functions that never return, and let the C stack itself model the CPS continuation without recursion depth ever mattering (see §4). CPS is powerful but invasive: it changes program representation and typically requires closure conversion and heap allocation of continuations, which is a bigger lift than trampolining for an existing tree-walker.

### 3.3 Restructure the eval loop around tail position
The technique actually used by most production tree-walkers and bytecode VMs (Guile, Python's frame-eval, Lua): keep `eval` recursive for *non-tail* subexpressions (operands, conditions, `let` bindings) but turn the *tail position* of `if`, `begin`, `let` bodies, and function bodies into a `loop { ... }` inside a single `eval` activation that just reassigns "current expression / current environment" and continues, instead of recursing. This is the "smallest change" family and is what section 6 proposes concretely for `agel-core`.

### 3.4 CEK machines and explicit continuation stacks
A CEK machine represents interpreter state as `(Control, Environment, Kontinuation)`, where `Kontinuation` is an explicit, heap-allocated data structure standing in for "the rest of the computation" instead of the host call stack ([CEK machine lecture notes, kmicinski.com](https://kmicinski.com/cis400-f21/assets/slides/cek.pdf); Racket continuations background at [khoury.northeastern.edu/.../cont.html](https://www.khoury.northeastern.edu/home/asumu/racket/reference/cont.html)). Because the continuation is a first-class heap value rather than the machine's call stack, tail calls are trivial (the continuation for a tail call is literally the same object, not a new frame), and full `call/cc` and even delimited continuations fall out naturally. The cost is that every non-tail call must reify a continuation frame on the heap instead of using the host stack — a bigger rewrite than a trampoline, but the "right" architecture for a language that wants first-class continuations. Notably, in Racket, `call/cc`'s own body runs in the *same* continuation as `call/cc`'s call site — `call/cc` itself introduces zero extra continuation frames — which is why CEK-style continuations and tail calls compose so cleanly.

### 3.5 Cheney on the M.T.A. (Chicken Scheme)
Henry Baker's two papers are the canonical reference: ["CONS should not CONS its arguments, or, a lazy alloc is a smart alloc"](https://www.cs.tufts.edu/~nr/cs257/archive/henry-baker/cons-lazy-alloc.pdf) and the sequel ["CONS should not CONS its arguments, part II: Cheney on the M.T.A."](https://dl.acm.org/doi/10.1145/214448.214454). Part II is the one CHICKEN Scheme implements ([wiki.call-cc.org/chicken-compilation-process](https://wiki.call-cc.org/chicken-compilation-process), [more-magic.net/posts/internals-gc.html](https://www.more-magic.net/posts/internals-gc.html)): compile Scheme to C via CPS, so every generated C function is `void`-returning and calls its continuation instead of returning; allocate all Scheme data (including activation "frames," which are now just C stack frames holding CPS continuation closures) on the C stack; when the C stack nears its limit, run a Cheney-style copying GC that treats the *live C stack* as the from-space and evacuates reachable data into the heap, then resets the C stack pointer to the bottom. Consequences: tail calls cost O(1) C stack space because C compilers turn self-tail-calls in a CPS-continuation style into loops/jumps (and even where they don't, the periodic GC reclaims the "stack" so it never actually overflows); first-class continuations are cheap to capture (no stack copying — activation records are already GC objects) but each one keeps its heap chain alive. This is an elegant unification of TCO + fast allocation + generational GC + cheap continuations, at the cost of a genuinely unusual runtime architecture (an explanatory HN thread: [news.ycombinator.com/item?id=8534381](https://news.ycombinator.com/item?id=8534381)).

### 3.6 Guile: bytecode VM with an explicit tail-call instruction
Guile's own manual is the cleanest "conventional" design point: the VM is a bytecode interpreter with a Scheme-to-bytecode compiler, and the ISA has separate `call` and `tail-call` opcodes — `tail-call` "simply shuffles down the procedure and arguments to the current stack frame" instead of pushing a new one ([Guile Reference Manual, Tail Calls](https://www.gnu.org/software/guile/manual/html_node/Tail-Calls.html); [Procedure Call and Return Instructions](https://www.gnu.org/software/guile/docs/docs-2.0/guile-ref/Procedure-Call-and-Return-Instructions.html)). Guile's VM hooks even expose the distinction observably: a non-tail call fires a "push-continuation" hook before the "application" hook, a tail call does not fire push-continuation at all. This is architecturally the closest existing design to what Agel's backend (B) is already doing with explicit `(tail-call f args)` IR nodes — Agel just needs the *codegen*, not the IR, to treat it as "reuse the frame" rather than "call normally."

## 4. How the major Schemes really do it (survey)

- **Guile**: bytecode VM, explicit `tail-call` instruction that overwrites the current frame's slots (§3.6).
- **Racket**: compiles through Chez Scheme's backend (since Racket CS); relies on the CEK/CPS-machine tradition and a real native-code compiler with tail calls as part of Chez's calling convention; `call/cc` and `call-with-composable-continuation` build on the same continuation representation, and delimited continuations (composable continuations "do not have a built-in abort" — [Racket docs on `cont.html`](https://www.khoury.northeastern.edu/home/asumu/racket/reference/cont.html)) are cheaper than full `call/cc` because they don't need to capture the entire stack.
- **Chez Scheme**: a genuinely optimizing native-code compiler; tail calls compile to jumps because Chez's calling convention makes the callee responsible for its own frame teardown and Chez's register allocator/frame layout is designed around it (this is the "just make your native calling convention support it" end of the spectrum, in contrast to Cheney-on-the-MTA's "make the whole runtime CPS" end).
- **Gambit**: also implements efficient `call/cc`; delimited-control implementations single out Gambit (alongside Chez, Scheme48, Larceny) as systems where shift/reset-style delimited continuations perform well specifically *because* the underlying `call/cc` is efficient ([okmij.org survey of delimited-control implementations](https://okmij.org/ftp/continuations/implementations.html)).
- **CHICKEN**: Cheney-on-the-MTA, described above.

Takeaway for Agel: there are two working philosophies, "compile tail calls into your native calling convention directly" (Guile/Chez/Gambit) and "restructure the whole runtime around CPS + a copying GC" (CHICKEN). Agel's constraints (small kernel budget, deterministic fuel/depth accounting, no established GC design mentioned in the prompt) point firmly at the first philosophy for both the Rust evaluator and the native backend.

## 5. `become` / `musttail`: guaranteed tail calls in mainstream compiled languages

- **LLVM `musttail`** (the `musttail` call marker) and **Clang's `[[clang::musttail]]`** attribute (on a `return` statement, not a function) guarantee tail-call elimination rather than leaving it to the optimizer's discretion — motivated exactly by "prevent stack overflow in iterative algorithms written recursively" ([blog.reverberate.org, "A Tail Calling Interpreter For Python"](https://blog.reverberate.org/2025/02/10/tail-call-updates.html); [LLVM review D99517](https://reviews.llvm.org/D99517)). It's now implemented in Clang, GCC, and reportedly an MSVC backend, and is under discussion for cross-compiler standardization ([LLVM Discourse, "Experience with `[[clang::musttail]]`"](https://discourse.llvm.org/t/experience-with-clang-musttail/89085)). Constraints are strict: matching signature/calling convention/ABI between caller and callee, verified at compile time (`clang::nonportable_musttail` relaxes this for backends — e.g. wasm without the tail-call extension — that can't guarantee it: [LLVM issue #72555](https://github.com/llvm/llvm-project/issues/72555)). CPython actually used `musttail` to build a tail-calling bytecode interpreter for exactly the reason Agel would want it — turning C-stack recursion in an interpreter's dispatch loop into guaranteed jumps.
- **Rust's `become` / explicit tail calls RFC**: tracked at [rust-lang/rust#112788](https://github.com/rust-lang/rust/issues/112788) and originally proposed in [rust-lang/rfcs#1888 / issue #1760](https://github.com/rust-lang/rfcs/issues/1760). Status as of the most recent activity: still an unstable nightly feature (`#![feature(explicit_tail_calls)]`), RFC not accepted; the compiler enforces that the callee's signature and calling convention exactly match the caller's ABI, with tail-call legality checks merged into rustc in December 2024. Rust has no *guaranteed* TCO in general because (a) `Drop` semantics — locals may need destructors run before a "tail" call, which is incompatible with just jumping — and (b) LLVM-level ABI matching constraints mean it can only ever be offered for a restricted, opt-in subset of calls (`become`), never as an automatic optimization on ordinary calls; note also open bugs even in the experimental feature, e.g. `become`ing a function that never returns ([rust-lang/rust#150243](https://github.com/rust-lang/rust/issues/150243)). **Implication for `agel-core`**: don't wait for `become` to stabilize — it doesn't fix a tree-walking interpreter's problem anyway, since the interpreter's own recursive `eval`/`apply` calls are what need to become loops, not a single hot function calling itself.
- **WebAssembly tail-call proposal**: adds `return_call` / `return_call_indirect` opcodes, semantically "same as `call`/`call_indirect`, but discard the caller's frame and replace the call with a jump" ([WebAssembly/tail-call proposal repo](https://github.com/WebAssembly/tail-call), [Overview.md](https://github.com/WebAssembly/tail-call/blob/main/proposals/tail-call/Overview.md)). V8 shipped it in v11.2 ([v8.dev/blog/wasm-tail-call](https://v8.dev/blog/wasm-tail-call)). Relevant to Agel only if/when Agel targets wasm as a compile output for the Agel-written backend — worth keeping the IR's `(tail-call f args)` node wasm-`return_call`-shaped now, since it costs nothing and pays off later.

## 6. Sibling-call optimization and differing arities

This is the crux for backend (B). The standard native-calling-convention description ([GCC internals, "Tail Calls"](https://gcc.gnu.org/onlinedocs/gcc-4.7.1/gccint/Tail-Calls.html); Cornell notes ["Proper Tail Calls on x64"](https://course.ccs.neu.edu/cs4410sp20/lec_tail-calls_x64_notes.html)) is:

- A **sibling call** is the restricted, always-safe case: caller and callee have compatible signatures (same argument-area size/layout, same calling convention), so the callee's argument area can simply overwrite the caller's in place, the return address is left untouched, and the call becomes `jmp callee` instead of `call callee; ret`.
- The general problem is the mismatch between **caller-pops** (standard C convention: caller cleans its own argument area after the call returns) and **tail-call needs callee-pops** semantics: "safe and efficient tail-call elimination assumes the callee pops the arguments" is a "fundamental tension" against the standard C convention. Concretely: if `G` tail-calls `H` and `H` takes *more* stack arguments than `G`'s own frame reserved, "there isn't enough room to replace the existing arguments with the intended new ones" — `F` (the original caller of `G`) will pop the wrong amount when `H` eventually returns to it, because `H`'s frame is a different size than `G`'s was.

Given Agel's convention today ("caller pushes closure then args, caller pops"), a naive in-place overwrite breaks the moment callee arity ≠ caller arity (almost always true for recursive calls with accumulators, mutual recursion between differently-shaped functions, etc.). Three concrete strategies, in increasing implementation cost:

1. **Callee-pops convention, fixed-size argument area reservation.** Switch the calling convention so the *callee* is responsible for popping its own arguments before returning (this is what classic Pascal/stdcall-style conventions do, and it is the precondition GCC's docs call out for safe tail calls). A tail call then becomes: write the new arguments into the current frame's argument area (growing the reserved argument-area down if the callee needs more slots than the caller reserved — this requires knowing at call-emission time the max argument count any tail-callee might need, or reserving generously), restore the static link/rbp linkage for the callee, and `jmp`. This is the standard "sibling call" shape and is what most native Schemes effectively do.
2. **Separate argument stack (a "value stack" distinct from the control/return-address stack).** Keep two stacks: one holds return addresses + saved rbp/static-link (rarely touched by tail calls, since tail calls by definition don't push a new return address), the other holds argument slots and is freely resized per call regardless of caller/callee arity mismatch, because it's not entangled with return-address bookkeeping. This is closer to how some bytecode VMs (and Forth-family designs) handle it, and it sidesteps the caller-pops/callee-pops tension entirely because "popping" the value stack back to the right depth is just resetting a stack-top pointer to a known frame-base value, independent of argument count. This is more mechanical sympathy with Agel's existing arrangement (rbp-based frames with an explicit static link already pushed under rbp) than a wholesale calling-convention rewrite.
3. **Argument copying through a scratch/red-zone area.** Compute all new argument values first into temporary registers/scratch stack slots (to avoid clobbering values still needed mid-evaluation), then memmove them into the frame's argument area at whatever size is needed, adjusting the stack pointer up/down as a final step before the jump. This is what many tail-call-supporting native compilers actually do at the codegen level regardless of convention (it's not really a fourth option so much as the mechanical implementation of options 1 or 2).

**Recommendation for Agel's backend**: option 2 (separate argument area from control area) is the best fit, precisely because Agel already has an explicit static link pushed under rbp — i.e., the backend already distinguishes "control linkage" from "argument/local data" conceptually. Concretely:
- Keep the return-address/saved-rbp/static-link chain untouched by a tail call (that's the entire point — no new control frame).
- Store incoming arguments in a frame-relative area whose *size the callee declares* (already known, since the backend is compiling an IR with typed/arity'd functions).
- Lower `(tail-call f args)` as: evaluate `args` into scratch registers/temp slots (already required for correctness — evaluating new args before overwriting old ones that might still be referenced), then bulk-copy into `f`'s expected argument-area layout at the *current* frame's base (growing/shrinking `rsp` to `f`'s argument-area size), then reload rbp/static-link for `f`'s def-context if it's a closure, then `jmp f`.
- Because "the callee's arity is known statically at the call site" (Agel is compiling a closed IR, not late-bound dynamic dispatch), you never need runtime arity negotiation — this is arguably easier than the general sibling-call problem GCC has to solve for separately-compiled C.

**Complexity estimate**: this is a localized change to one codegen rule (`(tail-call f args)` lowering) plus a frame-layout convention change (declaring argument-area size per function, and switching argument-area growth to be tail-call-aware). Given the backend is "written in Agel" and already has to represent code as a tree recursing by depth (per the 256-limit constraint mentioned in the prompt), and already has explicit tail-call IR nodes, ballpark: **150–400 lines of Agel** — roughly 50–100 lines for computing/declaring per-function argument-area size and emitting the frame prologue accordingly, 50–150 lines for the tail-call lowering rule itself (arg evaluation into scratch, bulk copy, rbp/static-link reload, jmp emission), and 50–150 lines of test/verification code (since getting frame-size math wrong is exactly the kind of bug that corrupts the stack silently). This is small relative to the rest of a backend, because the hard conceptual work (recognizing tail position, representing it explicitly in IR) is already done — only codegen needs to change.

## 7. Stack-safety approaches as alternatives/complements to true TCO

- **Stacker / segmented stacks (Rust)**: [`stacker`](https://docs.rs/stacker/latest/stacker/) (formerly `alexcrichton/stacker`) implements "manually instrumented segmented stacks": call sites are annotated "maybe grow the stack here," and if near the limit, a heap-allocated temporary stack is allocated and switched to for the duration of a closure (using the `psm` crate; Windows uses Fibers). `rustc` itself uses this internally (`rustc_data_structures::stack`) to survive deeply nested ASTs/types. This is not tail-call elimination — it's "make the stack effectively unbounded" — but it is a legitimate, much smaller patch for `agel-core` if proper tail calls turn out to be too invasive short-term: bump the *effective* stack for the evaluator thread rather than restructuring `eval`. It doesn't fix the *fuel/call-depth budget* semantics Agel wants (the 256 limit is a deliberate deterministic resource bound, not an accident of physical stack size), so it's a complement to, not a substitute for, real tail-call handling.
- **Heap-allocated frames / "stackless" interpreters**: **Stackless Python** decouples the Python execution stack from the C stack entirely — frame objects live on the heap, tasklets are lightweight cooperatively-scheduled "microthreads" that can number in the hundreds of thousands within ~100MB, with context switches over 1M/sec ([Stackless Python docs](https://stackless.readthedocs.io/en/latest/stackless-python.html); [Tasklets wiki](https://github.com/stackless-dev/stackless/wiki/Tasklets)). This is architecturally close to Agel's own agents-with-isolated-heaps-and-mailboxes model — Agel may already have "for free" what Stackless Python built tasklets to get: cheap, heap-based, schedulable units of control that don't need deep native call stacks per unit.
- **Erlang/BEAM**: each process gets its own small heap+stack (2 KB initial), and the scheduler preempts a process after a fixed reduction budget (~2000–4000, "roughly, function calls") rather than running to completion or stack exhaustion ([theBeamBook, scheduling.asciidoc](https://github.com/happi/theBeamBook/blob/master/chapters/scheduling.asciidoc); [AppSignal, "Deep Diving Into the Erlang Scheduler"](https://blog.appsignal.com/2024/04/23/deep-diving-into-the-erlang-scheduler.html)). Per-process GC means one process's pause never blocks others. BEAM itself *compiles* tail calls properly (Erlang, like Scheme, guarantees TCO in its semantics) — the reduction-count preemption is a separate, complementary mechanism for *time-slicing*, not a replacement for TCO. This maps almost exactly onto Agel's existing "deterministic fuel + per-agent isolated heap + deterministic scheduling" design — Agel's fuel counter is structurally BEAM's reduction counter, and Agel's call-depth budget is the piece BEAM doesn't need (because BEAM has real TCO, so call depth is never the limiting resource — only fuel/reductions are).

## 8. Smalltalk and Self: contexts as objects, mapped onto a stack

- **Cog VM (Squeak/Pharo/OpenSmalltalk)**: conceptually, "every method or block activation in Smalltalk is represented by a context object" with its own small stack of temporaries, chained via a `sender` slot — a fully reified, heap-like activation record model, exactly the kind of representation that supports arbitrary introspection/`thisContext` and cheap "resumable exceptions." But naively allocating a context object per call is slow, so Cog's Stack VM (and its JIT successor, the Cogit) does **context-to-stack mapping**: "the VM fools the image into thinking there are always contexts and only contexts when in fact the VM uses a much more conventional and much faster stack organization" ([OpenSmalltalk-vm README](https://github.com/OpenSmalltalk/opensmalltalk-vm/blob/Cog/README.md); [Cog Blog, "Under Cover Contexts and the Big Frame-Up"](http://www.mirandabanda.org/cogblog/2009/01/14/under-cover-contexts-and-the-big-frame-up/)). Contexts are materialized as real objects lazily, only when something (a debugger, `thisContext`, a captured continuation-like object) actually asks for one — otherwise activations live on a plain native stack. This "lazy reification" pattern is directly applicable to Agel: keep the fast path as flat native/interpreter frames, and only materialize a heap "context/continuation object" when something like a captured restart, a debugger, or a cross-agent handoff actually needs to inspect or resume an old frame.
- **Self**: the deeper academic source for "activation records as first-class, garbage-collectable objects" is Dybvig et al.'s ["Representing Control in the Presence of First-Class Continuations"](https://www.cs.tufts.edu/~nr/cs257/archive/kent-dybvig/stack.pdf) — the paper explicitly frames the problem as: any language whose control abstraction (Scheme's continuations, Smalltalk/Self's context objects) has "indefinite extent" cannot use "a simple stack-based implementation of call frames," and surveys strategies for reconciling reified control state with fast stack-like execution in the common case. Self's own VMs historically used similar stack-frame/heap-frame duality plus aggressive inlining (via customization and PICs) to keep deep call chains (Self programs are extremely call-heavy due to pervasive message sends for even trivial operations) cheap without paying the cost of full activation-record objects on every send.

## 9. Continuation-passing, delimited continuations, and agents/mailboxes as a cheaper alternative

Full `call/cc` is expensive to implement well precisely because it must be prepared to capture *the entire remaining computation*, including all pending non-tail-call frames — this is why efficient `call/cc` is a distinguishing feature of only a few Schemes ("only on systems that implement call/cc efficiently, such as Chez Scheme, Scheme48, Gambit, Larceny" — [okmij.org survey](https://okmij.org/ftp/continuations/implementations.html)). Delimited continuations (`shift`/`reset`, and the closely related "composable continuations" in Racket) are cheaper because the captured continuation is bounded by an explicit delimiter rather than reaching to the top of the world — but they still require *some* representation of "the stack between here and the delimiter" as a heap-movable value.

Agel's actual concurrency model — isolated per-agent heaps, mailboxes, deterministic scheduling, transactional per-form commit/rollback — already gives most of what people reach for full/delimited continuations *for* in practice: resumable, suspendable units of work that can be paused and handed off. Where a Scheme program would use `call/cc` or `shift`/`reset` to implement a generator, a cooperative scheduler, or backtracking search, an Agel program can often instead spawn an agent, communicate progress/results over its mailbox, and let the *existing* deterministic scheduler do the suspension/resumption — no continuation capture machinery needed at all. This suggests Agel should **not** prioritize general `call/cc` or delimited continuations as a language feature; the agent/mailbox primitive is a structurally cheaper way to get the same "pause and resume a computation" power for the use cases that matter (coroutines, generators, cooperative multitasking), and it composes naturally with the existing transactional/rollback semantics (an agent's turn is already an all-or-nothing unit, much like a delimited continuation's extent). Reserve continuation machinery only if a concrete use case needs *sub-agent-turn* suspension (e.g. resuming mid-expression after a signal is handled) — and even there, `with-handler`/`invoke-restart`'s existing non-local-control-transfer (which Agel already has) covers the classic "resumable exception" use case that Lisp/Smalltalk restarts and delimited continuations both target, without needing first-class continuations.

## 10. Concrete proposal for (A): the Rust tree-walking evaluator

Given a recursive `eval(expr, env, state) -> Result<Value, Signal>` and a transactional `State`, the smallest change that yields real tail calls for `if`/`begin`/`let`-body/function-body tail positions is the classic **"trampoline the tail position, keep everything else recursive"** restructuring (§3.3), *not* a full CPS or CEK rewrite:

1. **Wrap `eval` in an outer loop.** Change the signature conceptually to a loop that owns two mutable locals, `cur_expr` and `cur_env`, seeded from the arguments. The body of the loop is today's `eval` match statement, *except* that any branch which is currently `return eval(sub_expr, sub_env, state)` in tail position (the `then`/`else` of `if`, the last form of `begin`/`let`/a function body, and — critically — a direct self/other function call that is itself in tail position) is replaced with `cur_expr = sub_expr; cur_env = sub_env; continue;` instead of a recursive call. Every *other* call to `eval` (operands, non-tail subexpressions, arguments needing evaluation before a call) stays a genuine recursive Rust call, so the Rust call stack still grows for genuinely nested (non-tail) evaluation — exactly matching R7RS's model where only tail calls are unbounded.
2. **Function application in tail position (`apply`) becomes a loop-continue too**, not a `Result`-returning recursive call: when `apply(f, args)` is invoked from a tail position, instead of recursively evaluating `f`'s body via a nested `eval` call, splice `f`'s body and a freshly-built environment into `cur_expr`/`cur_env` and `continue` the same top-level loop. This is exactly Guile's `tail-call` bytecode op (§3.6) translated into "reuse the same Rust stack frame" instead of "reuse the same VM frame."
3. **Call-depth accounting**: today, presumably, each `eval`/`apply` recursion increments a depth counter that's decremented on return, bounding Rust stack usage at 256. Once tail positions become loop iterations instead of recursions, they must **stop incrementing call-depth** — the loop iterating 1000 times should cost the same one unit of Rust-stack-depth it always did, matching R7RS's "no space is needed for an active tail call" requirement. Concretely: increment the depth counter only at the *recursive* `eval` call sites that remain (non-tail evaluation), never at the loop-continue points. This is the one-line semantic change that actually delivers "proper" tail calls rather than just "faster" ones — depth must track genuine Rust-stack nesting, not "number of logical calls performed."
4. **Fuel** needs no special treatment: fuel already presumably decrements per `eval` step/form regardless of whether that step recurses or loops, so an unbounded tail-recursive loop still terminates (deterministically) when fuel is exhausted — this is actually the more fundamental reason it's safe to make tail calls "free" in Agel: fuel remains the resource that guarantees termination/boundedness of a turn, while call-depth becomes purely a measure of *non-tail* nesting (protecting the *physical* 4 MiB Rust stack against genuinely deep — not tail — recursion, e.g. deeply nested arithmetic expressions or non-tail recursive functions like naive `map`).
5. **`with-handler` dynamic extent**: this is the trickiest interaction. `with-handler`/restart installation presumably works today by pushing a handler/restart record that is popped when the corresponding Rust `eval` call returns (RAII-style, tied to a Rust stack frame's lifetime) — i.e., "dynamic extent" is currently *identified with* Rust-stack extent. Once a function's tail call can loop-continue out from under an active `with-handler` block without a Rust frame ever returning, dynamic-extent tracking must be moved from "implicit, tied to the Rust call stack" to an **explicit handler/restart stack living in `State`**, pushed/popped by the interpreter loop itself rather than by Rust's own stack unwinding. Concretely: a `with-handler` form's tail-position body must, on entering the loop-continue path, push its handler frame onto an explicit `Vec<HandlerFrame>` in `State` (as it presumably already does or should), and — the new requirement — the loop must know to pop that frame when control tail-exits the dynamic extent of the `with-handler` form (i.e., when `cur_expr`/`cur_env` are overwritten by a tail call whose target is *outside* the `with-handler`'s body, not merely when a Rust function returns). This means tail positions *inside* a `with-handler` body remain tail positions (good — a loop inside a handler shouldn't grow stack), but a tail call *out of* the dynamically-enclosing `with-handler` scope must be recognized at the point of the jump and trigger a handler-frame pop, not left to Rust's `Drop`/unwind machinery (because there may be no unwind — the loop just re-targets `cur_expr`). This is exactly the same "explicit stack instead of implicit host-stack" move CEK machines make (§3.4), scoped narrowly to *just* handler/restart bookkeeping rather than the whole interpreter.
6. **Agent turns and transactional worlds**: unaffected in principle — a turn's outer transactional boundary is already presumably a Rust-level call around the top-level `eval` loop per form, and this proposal only changes what happens *inside* a single top-level form's evaluation, not the commit/rollback boundary around it. The one thing worth auditing: if rollback logic today relies on "count of Rust stack frames unwound" as a signal for how much state to undo, it should instead rely purely on `State`'s own transactional log (which it should already do, given per-form commit/rollback is a stated design goal) — this proposal doesn't need to touch that, but it's worth confirming the rollback path doesn't secretly depend on Rust stack depth anywhere near handler/restart code.

This is a genuinely small, local change — it touches `eval`'s dispatch loop and the handler/restart push/pop discipline, not the value representation, environment representation, or fuel model. It's the same shape of change Guile's bytecode `tail-call` instruction represents, just implemented directly in the tree-walker's own dispatch loop instead of in a separate bytecode ISA.

## 11. Concrete proposal for (B): the Agel-written x86-64 backend

See §6 for the full design (separate argument area from the control/static-link chain, callee declares its argument-area size, tail-call lowering evaluates new args into scratch then bulk-copies into place before `jmp`). Summary of the frame layout change:

- **Today**: caller pushes closure, then args; callee's rbp-based frame with static link under rbp; caller pops (implying a caller-pops convention incompatible with safe tail calls per §6).
- **Proposed**: keep the rbp/static-link control chain exactly as-is for *non-tail* calls (no change needed there — this is what handles genuinely nested/non-tail invocations, which still need real frames). For calls compiled from `(tail-call f args)` IR nodes specifically: reuse the current frame's argument-area slot (resized to `f`'s declared arity/argument-area size), reload the static link for `f`'s definition environment, and `jmp` rather than `call`. Because Agel's IR already marks tail position explicitly, the backend never needs runtime arity discovery or a general "is this safe as a sibling call" analysis (the hard part of doing this for e.g. C/C++) — arity and frame-size are compile-time facts.
- **Estimated complexity**: ~150–400 lines of Agel (see §6), concentrated in the `(tail-call ...)` lowering rule and per-function argument-area-size computation; this is small because the IR-level tail-position analysis is already done upstream — only the final x86-64 emission rule for that one IR node needs to change from "call+ret" to "copy args + jmp."
