# REALTALK, Dynamicland, and live whole-system computing: what an AI-native OS should take

## 1. Dynamicland and Realtalk

### 1.1 The physical computing model

Dynamicland is a nonprofit research lab and public space in Oakland/Berkeley, led by Bret Victor's group (formerly part of YC Research/HARC), built on the premise that "a computer is a place, not a device" — a communal computer that a whole room of people programs together with paper, pens, and physical objects rather than screens ([dynamicland.org](https://dynamicland.org/), [Carl Tashian, "At Dynamicland, The Building Is The Computer"](https://tashian.com/articles/dynamicland/), [Hackaday, "Dynamicland Makes The Whole Building The Computer"](https://hackaday.com/2021/09/18/dynamicland-makes-the-whole-building-the-computer/)). Cameras and projectors overhead read markers ("colored dots") on sheets of paper and project computed imagery back onto the same paper, so a piece of paper *is* a running program: pick it up, move it, tear it, and the computation follows. The FAQ is explicit that this is not metaphorical: "every running program is a real thing which is organized, inspected, and edited in the real world" and the Dynamicland website itself is "made entirely in Realtalk" as a physical artifact ([Dynamicland FAQ](https://dynamicland.org/2024/FAQ/)).

Realtalk is the software substrate underneath this: described by its own authors as "the world's only self-hosted spatial computing system," and framed in their own materials as "an operating system for communal computing" (see the 2024 talk PDF, [dynamicland.org/archived-media/2024/09/DL2024-09-04-bc5875.pdf](https://dynamicland.org/archived-media/2024/09/DL2024-09-04-bc5875.pdf); project page [harc.ycr.org/project/realtalk](https://harc.ycr.org/project/realtalk/)).

### 1.2 Pages as programs

The unit of computation in Realtalk is the **page** — a sheet of paper (or any trackable object) with a fiducial marker. A page carries a script that runs every frame the page is detected by a camera ([ElephantTalk implementation notes, github.com/deosjr/elephanttalk](https://github.com/deosjr/elephanttalk)). "Arranging spatial relationships among programs is itself a kind of programming" — proximity, overlap, and orientation between pages are inputs to the system, not metadata about it ([Is Realtalk open source?, dynamicland.org/2024](https://dynamicland.org/2024/Is_Realtalk_open_source/)). There is no file tree: the architecture "explicitly rejects traditional file-tree structures," because a hierarchy would reintroduce a hidden, non-physical place where state "really" lives.

### 1.3 The claim / wish / when reactive model

Realtalk's coordination language is a small reactive, Datalog-like rule system built on three primitives (this is the best-documented technical detail publicly available, largely reconstructed by outside re-implementers since Dynamicland does not publish the real source; see [ElephantTalk — "A Gopher's Adventures in Dynamicland"](https://github.com/deosjr/elephanttalk) and [Tabula Luma on Hackaday](https://hackaday.io/project/204937-tabula-luma-inspired-by-realtalk)):

- **claim**: a statement of fact currently true about the world — "this page is at x,y", "this block is a `+` operator", "the temperature sensor reads 21°C." Claims are asserted by *some* program and are visible to everyone.
- **wish**: a statement of a desired state — "I wish the light were on," "I wish this cell's value were 5." A wish is a request, not a command.
- **when**: a rule of the form "when \<pattern over claims/wishes matches\>, do \<claim/wish more things\>." `when` clauses are pattern-matched against the live claim/wish set using logic-programming (Datalog-style) unification rather than imperative control flow — "a loose, decentralized group of physical objects, noticing aspects of the physical world and wishing for the world to be different" (FAQ). ElephantTalk's author independently rebuilt this as "a very simple datalog instance" embedded in a Lisp dialect, which is the closest public description of the semantics; the real Dynamicland system's exact matcher and query planner are unpublished.

This gives Realtalk an entirely **declarative, fact-oriented programming style**: instead of calling a function, a page claims or wishes something, and other pages' `when` rules react. Nobody "calls" anybody; there is no direct addressing, only shared visibility of the claim/wish store.

### 1.4 Concurrency, liveness, and "no hidden state"

Every page's script, and every `when` rule system-wide, is **recomputed from scratch every camera frame** (Realtalk historically ran at video frame rate, tens of Hz). There is no persistent object graph carried imperatively across frames the way a normal program's heap is; instead the claim/wish database is largely re-derived each tick from current physical/sensor state and current rule outputs, and rules quiesce to a fixed point within the frame. This sidesteps most classical concurrency problems (locks, races, stale caches) because there is no long-lived mutable state to race over — state *is* the current frame's fully-recomputed claim set. ElephantTalk's re-implementation explicitly notes "no state is persisted between frames" as the operating assumption it copies from the original.

Liveness is total: "All programs, anywhere in the system, in any language, are live-editable, recompile instantaneously, live-display their state" (FAQ). Debugging is not stepping through invisible call stacks; you can see, physically, which page or process wrote which claim, right there on the table. This is close to what the community calls **provenance** — although Realtalk's own materials don't use that exact phrase, the design principle they push hardest is transparency of authorship: the whole point of laying claims out as visible physical/projected annotations is that anyone in the room can ask "who said that?" by looking at which page or process is currently asserting a given claim, and watch it update live. The FAQ states the philosophical converse bluntly: "people do not generally issue commands in Realtalk, because there is no disembodied state to command" — i.e., there is no hidden state *by construction*, because all state is either a physical object or a claim visibly projected next to the thing it describes.

### 1.5 Community of computers, not a personal computer

Dynamicland deliberately rejects the personal-computer and client-server models. "Every site has its own independent physical copy of Realtalk. People share updates by getting together and talking about them" (FAQ). This is the "community of computers" idea: computation is inherently plural, local-first, and social — code and data propagate by human contact and shared physical rebuilding, not by a central repository or network sync. The team is explicit that they will not put Realtalk on GitHub, arguing that doing so "would open it up... only to the computing culture that we're trying to create an alternative to" — i.e., open-sourcing the artifact without open-sourcing the *practice* of building it together would just reproduce ordinary software culture ([Is Realtalk open source?](https://dynamicland.org/2024/Is_Realtalk_open_source/), also mirrored as a gist explaining the reasoning: [gist.github.com/shaunlebron](https://gist.github.com/shaunlebron/4b9a9a986fca1e7abd0bfcadbedaa526)).

### 1.6 Implementation: what's publicly known

Realtalk-2020 ("Realtalk-2020") was a from-scratch rewrite that Dynamicland began around July 2019, superseding the pre-2019 prototype (sometimes called "Realtalk 2017", archived at [dynamicland.org/archive/2017/Realtalk](https://dynamicland.org/archive/2017/Realtalk)). Publicly confirmed technical facts are sparse by design: process/"leaf" languages historically included Lua (a documented "superset of Lua" per third-party notes), C, C++, Python, JavaScript, Julia, and Haskell as guest languages for individual page scripts, with a separate small coordination language for claim/wish/when; the team has said Realtalk-2024 aims to replace all of those with its own dedicated process language because "all these languages are off-putting for many people" (FAQ). There is no public git repository, no public source release, and no formal paper describing the current matcher/scheduler; nearly everything cited above comes from talks, the FAQ, blog write-ups by visitors (e.g. [Omar Rizwan's notes from Dynamicland](https://omar.website/posts/notes-from-dynamicland-geokit/), [Andy Matuschak's notes](https://notes.andymatuschak.org/zDpmsw9zxmk2eXsoHVUqidf)), and outside reconstructions like ElephantTalk (Go) and Tabula Luma (a from-scratch reimplementation, [hackaday.io/project/204937](https://hackaday.io/project/204937-tabula-luma-inspired-by-realtalk)). This opacity is itself a design statement discussed above (§1.5) and a real limitation for anyone trying to borrow the mechanism precisely rather than the idea.

## 2. Comparable live, whole-system environments

### 2.1 Croquet / TeaTime — deterministic replicated computation

David P. Reed, Alan Kay, and David A. Smith's Croquet Project (early 2000s) built a shared 3D collaborative OS whose core synchronization mechanism, **TeaTime**, makes every participant run a "bit-identical instance of a shared virtual computer": all machines execute the same deterministic simulation in lock-step, driven by a shared logical clock from a lightweight external "Reflector" server that only orders and timestamps messages — it never touches application state ([Smith, "Croquet: A Collaboration System Architecture," VPRI TR-2003-001](https://tinlizzie.org/VPRIPapers/tr2003001_croq_collab.pdf); [Wikipedia, Croquet Project](https://en.wikipedia.org/wiki/Croquet_Project); [Wetmachine, "Controlling Time: TeaTime"](https://wetmachine.com/inventing-the-future/controlling-time-teatime/)). Because state changes only through message delivery order (not through the message *contents* needing to be replayed exactly, but through every replica agreeing on delivery order and applying deterministic transition functions), two machines that start identical and receive the same ordered message stream stay identical forever without ever exchanging bulk state. This is essentially lockstep networking as used in RTS games, generalized into an OS-level object model. The idea traces to Reed's 1978 MIT PhD thesis on naming and synchronization in decentralized systems. This is **extremely close to Agel's own replay model**: Agel's `World::replay` takes an ordered transaction-input log and a snapshot and reproduces state deterministically, with a checksum to detect divergence (`docs/architecture.md`, `docs/agent-runtime.md`) — Croquet/TeaTime is the direct historical precedent for extending that from single-machine replay to *multi-machine, real-time, lockstep replication*.

### 2.2 Erlang/OTP — supervision, isolation, hot loading

Erlang (Ericsson, late 1980s, formalized by Joe Armstrong's 2003 thesis "Making reliable distributed systems in the presence of software errors") gives each process its own heap so a crash cannot corrupt another process's memory and there is no global GC pause; OTP's **supervision trees** structure a system into workers (do computation) and supervisors (restart failed children per a declared strategy) so that failure handling is separated from business logic — "let it crash" means isolate and recover, not ignore errors ([Erlang System Documentation, Design Principles](https://www.erlang.org/doc/system/design_principles.html)). **Hot code loading** lets a running system swap module versions without stopping. Agel's agent runtime already mirrors the isolated-heap-plus-supervision half of this closely (`docs/agent-runtime.md`: isolated persistent heaps, `restart`/`stop`/`escalate` policies, supervisor trees that cannot cycle) — the piece Erlang has that Agel does not yet foreground is hot code loading as a first-class, low-ceremony operation across a live population of agents (Agel currently does this at the world/image level via canonical world files and A/B promotion, which is coarser-grained than per-module code swap).

### 2.3 Plan 9 — everything is a file, namespaces per process

Plan 9 (Bell Labs) generalized Unix's "everything is a file" so thoroughly that network connections, window systems, and even other machines' resources are addressed through the 9P file protocol, and, critically, **each process has its own private, mutable namespace** built by mounting and binding resources — "each process has its own private machine" ([The Use of Name Spaces in Plan 9, 9p.io](https://9p.io/sys/doc/names.html); [Matt Rickard, "Plan9: Everything is (Really) a File"](https://mattrickard.com/plan9-everything-is-a-file)). Agel already has per-process namespaces as a capability-scoped concept (`docs/architecture.md`: "resolves through a namespace capability; there is no ambient root" — a POSIX path only resolves through a namespace capability a process was granted, per `docs/design-lineage.md`'s note on Redox). Plan 9 is confirmation that this is a proven, composable idea at OS scale, and its main lesson for Agel is that *namespaces compose via explicit union/bind operations* — worth stealing as a vocabulary even where Agel's authority model (capability-as-slot, not capability-as-name) is deliberately stricter than Plan 9's (a 9P name is itself often the only checked token).

### 2.4 Oberon — the whole OS as one live language

Niklaus Wirth and Jürg Gutknecht's Oberon System (ETH Zürich, ~1985-88) is written almost entirely in the Oberon language itself, with assembly reduced to bootloader/device-driver/GC bare essentials; "its simplicity and clarity enables a single person to know and implement the whole system" ([Wikipedia, Oberon (operating system)](https://en.wikipedia.org/wiki/Oberon_(operating_system)); [Wirth & Gutknecht, *Project Oberon*](https://people.inf.ethz.ch/wirth/ProjectOberon1992.pdf)). It demonstrates that a small, single-language, single-person-comprehensible OS is achievable and that comprehensibility is itself a security and correctness property — directly relevant to Agel's own goal of a self-hosting compiler/backend small enough that "the whole system" including its own compiler runs inside itself (`docs/agel-in-agel.md`, `docs/self-hosting-performance.md`).

### 2.5 Smalltalk-80 and Lisp machines — the image as the whole world

Smalltalk-80's "live system" persists the entire runtime — every object, in its current state — into a single image file; "saving the image means the next time you open the system, you continue right where you left off... as if you had frozen time" (search synthesis via [ST80 VM project](https://github.com/devhawala/ST80), [VisualWorks](https://en.wikipedia.org/wiki/VisualWorks)). Lisp machines took this further, making the OS *and* the debugger *and* the language runtime one live, inspectable, redefinable Lisp image with no boundary between "running program" and "development environment." Agel's canonical world files (`World::to_canonical`/`from_canonical`, `docs/architecture.md` item 78) are a modernized, content-addressed, versioned descendant of this idea — the delta encoding (`to_canonical_over`) is actually a refinement Smalltalk images never had (incremental, diffable saves rather than one monolithic blob).

### 2.6 Unison — content-addressed code, no builds

Unison identifies every function by a hash of its own syntax tree rather than by a mutable name, so code lives in a content-addressed database, dependencies are pinned by hash, and there is no build step because code is already stored compiled/type-checked ([unison-lang.org, "The big idea"](https://www.unison-lang.org/docs/the-big-idea/); [GitHub, unisonweb/unison](https://github.com/unisonweb/unison)). This is a strong complement to Agel's SHA-256 canonical world hashing (`docs/architecture.md`: "evidence to a world state is SHA-256 over a canonical, versioned" encoding) — Unison content-addresses *code*, Agel content-addresses *world state*; combining both (content-addressed bindings *inside* a content-addressed world) would give Agel Unison-style "no builds, no naming collisions, structural sharing" for the code an agent writes, on top of what it already has for whole-world snapshots.

### 2.7 Nix — reproducible derivations

Nix builds packages as pure functions of their inputs into an immutable, content-addressed `/nix/store`, eliminating shared mutable system state and making builds reproducible bit-for-bit ([Nix Reference Manual, content-addressing derivation outputs](https://releases.nixos.org/nix/nix-2.31.0/manual/store/derivation/outputs/content-address.html); [Tweag, "Implementing a content-addressed Nix"](https://www.tweag.io/blog/2021-12-02-nix-cas-4/)). The relevant lesson for Agel is packaging/installation determinism: Agel's "programs installed from files" (v0.2.84, per git history) and its C library/ELF process story should ideally converge on Nix-like content addressing for installed artifacts, so that "the program the agent installed" is exactly reproducible and diffable the same way a world file is.

### 2.8 Boxer and HyperCard — end-user liveness and legibility

HyperCard (Apple, 1987) gave non-programmers an English-like scripting language (HyperTalk) where "the state of any object was considered to be live and editable at any time" ([CACM, "The Role of Hypercard in Today's World"](https://cacm.acm.org/blogcacm/the-role-of-hypercard-in-todays-world/)); Boxer let users nest GUI objects ("boxing") and name them for direct reference in code, mixing graphical and textual programming. Both prioritized **legibility for non-experts** over raw power — directly analogous to what an agentic OS needs when the "programmer" writing code at runtime is sometimes an LLM and sometimes a human reading what the LLM wrote: the artifact must stay legible to the human even though it was authored by a model.

### 2.9 Urbit — deterministic functional OS, skeptically

Urbit's Arvo is "an axiomatic operating system which restricts itself to pure mathematical functions, making it deterministic," compiled through Hoon down to Nock, a tiny fixed combinator calculus meant to be a permanent, hardware-independent target ([docs.urbit.org/urbit-os/kernel/arvo](https://docs.urbit.org/urbit-os/kernel/arvo); [Urbit, "Why Hoon?"](https://urbit.org/blog/why-hoon)). The strongest public criticism is that Hoon's syntax is "totally incomprehensible to anyone who hasn't read through every bit of the documentation," making independent security review effectively impractical without months of investment ([HN discussion, "Urbit: The good, the bad, and the insane"](https://news.ycombinator.com/item?id=27268462); Urbit's own rebuttal in ["Common Objections to Urbit"](https://urbit.org/blog/common-objections-to-urbit) concedes the syntax cost but argues it's a one-time tax). The lesson for Agel is a caution, not an endorsement: full determinism-by-construction (Agel already has this via fuel budgets and canonical replay) is worth having, but it must not come bundled with an idiosyncratic notation that only its own authors can audit — Agel's Lisp syntax and existing Common Lisp lineage (`docs/design-lineage.md`) is the safer choice here precisely because it is legible to outsiders and to the LLMs that will read and write it.

### 2.10 Xerox Cedar/Mesa

Cedar (Xerox PARC, late 1970s–80s) was an attempt to reconcile three incompatible PARC programming cultures — Mesa (strongly typed systems language), Interlisp, and Smalltalk — into one live, strongly-typed, garbage-collected environment with an integrated debugger and incremental compilation ([Swinehart, "A Structural View of the Cedar Programming Environment"](https://worrydream.com/refs/Swineheart_1986_-_A_Structural_View_of_the_Cedar_Programming_Environment.pdf)). Its lesson for Agel, which is deliberately a *single* language end-to-end (kernel, compiler, backend, desktop, DOOM agent all in Agel itself, per `docs/agel-in-agel.md`), is largely a warning about the cost Cedar paid trying to bridge multiple language cultures live in one image — a cost Agel avoids by having only one language, but should keep in mind if it ever needs to host guest languages (as Realtalk does with Lua/Python/etc. per-page).

### 2.11 Recent "AI-native OS" attempts

Andrej Karpathy's September 2023 "LLM OS" sketch treats the LLM itself as a CPU/kernel process, the context window as RAM, retrieval/file access as disk, and tool calls as peripherals/syscalls ([Cam Pedersen, "What would an LLM OS look like?"](https://campedersen.com/llm-os); [Hugging Face, "Illustrated LLM OS"](https://huggingface.co/blog/shivance/illustrated-llm-os)). This framing is popular but mostly stops at analogy: it does not specify determinism, replay, or authority — the LLM "kernel" is itself nondeterministic, so nothing built strictly on that metaphor inherits reproducibility. OpenAI's Agents SDK "sandbox agents" attach capability-scoped tools (filesystem, shell, memory, skills) to a live sandbox session and can bind MCP servers as additional tool sources ([OpenAI Agents SDK, Sandbox capabilities](https://openai.github.io/openai-agents-python/ref/sandbox/)) — a workable capability-like model for *tools*, but with no equivalent of Agel's typed effect boundary, fuel budget, or canonical replay; state consistency across long agent runs is handled ad hoc via "durable execution," checkpoints, and retry logic rather than deterministic replay (Anthropic's own writeup on its multi-agent research system candidly notes multi-agent systems are "non-deterministic by design" and that engineering effort went into resuming from failure points and informing agents of tool failures rather than eliminating nondeterminism — [Anthropic, "How we built our multi-agent research system"](https://www.anthropic.com/engineering/multi-agent-research-system)). The common failure mode across these systems: state lives in an opaque conversation/context blob plus scattered tool side effects, with no canonical, replayable, content-addressed record of "what happened" and no first-class notion of provenance for any given fact the agent is relying on — exactly the two things Realtalk is strongest at (liveness/no-hidden-state, and implicit provenance-by-visibility) and exactly the two things current agent frameworks are weakest at.

## 3. Synthesis: what an LLM-agent OS needs

Putting these together, an OS whose primary "programmer" is an LLM agent (sometimes acting alone, sometimes alongside a human) needs, in rough priority order:

1. **Deterministic replay of everything an agent did.** Agel already has this: fuel-bounded evaluation, an event log per world branch, `World::replay` against an ordered transaction-input log with a divergence checksum, and (per `docs/agent-runtime.md`) a model-effect journal (`model-requested`/`model-dispatch-started`/`model-completed`/`model-failed`/`model-delivery-dropped` events) that lets *even nondeterministic model calls* be replayed by replaying the recorded completions rather than re-invoking the model. This is the single most important property none of the LLM-OS/agent-sandbox proposals above have, and it is closest in spirit to Croquet/TeaTime's insistence that a shared computation is defined by an ordered message log, not by ambient mutable state.

2. **Capability-scoped effects.** Agel already has this via its `agel-effects` typed-effect boundary and per-process namespace capabilities (`docs/architecture.md`, `docs/design-lineage.md`'s seL4/Microkit lineage) — a word must hold a capability of a kind to touch a file, the clock, or the console. This is stricter than what OpenAI's sandbox-tool model or MCP servers provide (those are closer to Plan 9's name-based authority than seL4's slot-based authority) and is a genuine Agel strength worth publicizing.

3. **Provenance of every fact/claim.** This is Realtalk's clearest advantage and Agel's clearest gap. Agel's event log records *what happened* (spawn, enqueue, commit, restart) but does not currently give a queryable answer to "who currently claims X is true, and why" for ordinary bindings and data the way Realtalk's claim store does for physical facts. Nothing in Agel today plays the role of "who said that" for a binding's current value — you can replay history to reconstruct it, but there's no live, first-class provenance record attached to the binding itself.

4. **A rule-based reactive layer over the actor/mailbox layer.** Agel's agents are message-passing actors (Erlang-like): good for isolation and supervision, but each interaction needs an explicit sender and message tag. Realtalk's claim/wish/when adds a second, complementary layer: facts asserted into a shared space, and rules that react to *patterns* over that space without either side needing to know the other's identity. These are not competitors — Realtalk's own coordination language sits *above* individually-scripted per-page processes, much as a claims/wishes library could sit above Agel's existing agents.

5. **Whole-system liveness and image persistence.** Agel's canonical world files, revision-checked commits, and A/B promotion are a modern, content-addressed, incremental version of the Smalltalk/Lisp-machine image. The gap relative to Smalltalk/Oberon is less about mechanism and more about *reach*: Smalltalk-80's image covered literally everything including the IDE; Agel's world covers language state and agents but the native kernel/QEMU layer sits outside it as a separate boundary (correctly, for the seL4-style reasons in `docs/design-lineage.md`).

6. **Human-legible state, no hidden state.** Realtalk's strongest philosophical commitment — nothing computational exists that isn't visible and physically pointed-to — maps to a concrete Agel requirement: every piece of state an agent or a human can affect should be reachable through the same inspection path (`event-log`, `agent-info`, canonical world dump), never squirreled away in a native side-channel. This is largely satisfied today but is worth treating as an explicit invariant to test against as new native modules are added.

7. **"The software the agent wrote or ported must be runnable."** Agel's install-from-file mechanism, ELF process support, and Redox-derived C library (`relibc`-inspired, per `docs/design-lineage.md`) already deliver on this in the POSIX-personality sense. The comparable systems above (Nix, Unison) suggest the next increment is making *what got installed* content-addressed and diffable the same way a world file already is, so "the agent installed program X" is as replayable and auditable as "the agent ran world transaction Y."

## 4. Recommendations for Agel

Prioritized, with rough cost and what to avoid.

1. **A Realtalk-style claims/wishes store as an `agel/claims` library over existing agents.** *(High value, medium cost.)* Implement `claim`, `wish`, and `when` as ordinary Agel functions/macros operating over a shared, capability-gated map-of-facts (a small Datalog-ish matcher, not a general logic engine), with each claim tagged with its asserting agent id and the world revision it was asserted in — giving "who said that" for free as a query rather than a log-replay exercise. Build it as a library on top of the existing mailbox/turn machinery (a `when` rule compiles to an agent that re-evaluates its pattern on relevant claim-store commits), not as a kernel change. *Avoid*: reimplementing Realtalk's frame-driven "recompute everything every tick" model wholesale — Agel's turn-based, fuel-metered scheduling is a better fit than continuous polling; instead trigger `when` re-evaluation on commit of matching claims, which is strictly less wasteful and still live.

2. **Provenance records on every binding/claim.** *(High value, low-medium cost.)* Extend the existing event-log format so that any `def`/claim carries `(asserted-by agent-or-toplevel, world-revision, evidence)` metadata, queryable without full replay. This is a natural companion to item 1 and also strengthens the existing canonical-world audit story (`docs/architecture.md` item on SHA-256 evidence) by making provenance a per-fact property, not just a per-world property. *Avoid* over-engineering this into a full temporal/bitemporal database; a revision number plus asserting-agent id, indexed for point lookups, covers the "who said that" use case Realtalk cares about.

3. **Croquet/TeaTime-style deterministic replicated worlds across machines.** *(High value, high cost.)* Agel's single-machine replay (snapshot + ordered transaction-input log + checksum) is already TeaTime's core idea minus the network. A follow-on experiment: a thin "Reflector"-equivalent service that only orders and timestamps transaction inputs across multiple Agel runtimes, letting two machines run bit-identical worlds without exchanging bulk state — directly reusing the existing replay machinery rather than inventing new sync logic. *Avoid* building a general CRDT/OT layer; TeaTime's lesson is that ordering discipline plus determinism is sufficient and much simpler than conflict-resolution machinery, provided every effect stays inside the deterministic core (exactly Agel's existing typed-effect boundary).

4. **A "page" model for programs, as an experiment, not a rewrite.** *(Medium value, medium cost, exploratory.)* Represent a self-contained unit of agent-authored software (a script plus its declared capabilities and its claim/wish rules) as a single addressable, physically-metaphor-free "page" object with its own visible state — useful chiefly as a UI/legibility device in the desktop/workshop (`docs/agentic-desktop.md`) so a human watching an agent work can point at one artifact and see everything it currently claims, wishes, and owns, the way a Dynamicland visitor can point at a sheet of paper. *Avoid* chasing the physical/camera-projector hardware angle — Agel's OS runs in QEMU/on real hardware but has no reason to reproduce Dynamicland's optical tracking; only the *legibility* property is worth porting, not the medium.

5. **Content-addressed code (Unison-style) inside a content-addressed world (Nix/Agel-style).** *(Medium value, medium-high cost.)* Hash individual bindings/functions by their canonical AST, not just the whole world, to get structural sharing across world revisions and installed programs, and to make "the agent installed program X" (item 7 above) diffable the same way world files already are. *Avoid* doing this before the claims/provenance work above — content-addressing code without provenance-of-claims still leaves "who asserted this fact is true" unanswered, which is the more urgent gap.

6. **Hot code loading across a live agent population (Erlang-style), distinct from world-level A/B promotion.** *(Lower priority, medium cost.)* Agel's current code-upgrade story is world/image-grained (`docs/native-code-upgrades.md`); a finer per-behavior hot-swap (a running agent's behavior closure is replaced without restarting the agent or the world) would close a real gap relative to OTP. *Avoid* introducing this before supervision/restart semantics are exercised further in production-like workloads — Erlang's hot loading works because its supervision discipline is mature; sequencing matters.

7. **What to avoid outright.** Do not adopt Urbit's approach of a bespoke, hard-to-audit notation in the name of purity/determinism — Agel's existing Lisp syntax is a genuine asset for LLM legibility and human review, and determinism is already achieved through fuel/canonical-replay rather than through an exotic combinator calculus. Do not adopt Dynamicland's anti-openness stance on distribution — Agel's project shape (per user's own memory notes: "one release per milestone with honest docs") is the opposite bet and should stay that way; Realtalk's opacity is a defensible choice for a research collective, not a template for a project whose whole feature is that an LLM agent (an outsider by construction) must be able to read, port, and run software inside it.
