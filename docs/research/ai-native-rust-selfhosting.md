# Agel research brief: AI-native language design, Rust as substrate, and self-hosting

## Part 1 — What a language for LLM-agent programmers needs

### The design landscape

**Verse (Epic Games).** Verse is a functional-logic language — "like Curry or Mercury" — designed with Simon Peyton Jones, built for Fortnite's persistent multiplayer worlds. Its defining move is putting transactions in the type system rather than treating them as a library concern: every function runs inside an atomic, rollback-able transaction; the `<decides>` effect marks functions that can fail, and failure propagates as backtracking rather than exceptions; `<transacts>` methods roll back automatically on failure, and this extends even to C++ called from Verse ([Book of Verse](https://verselang.github.io/book/00_overview/), [Verse type system](https://brianmckenna.org/blog/verse_types), [UnrealVerseGuru notes](https://github.com/UnrealVerseGuru/VerseProgrammingLanguage)). This is close to Agel's per-form/per-turn commit-or-rollback world model, but Verse goes further by making "this function can fail and be retried" a *type-level* fact instead of a convention — something Agel's evaluator currently enforces operationally (conditions/restarts) but does not yet expose to static checking.

**Koka (Microsoft Research / Daan Leijen).** Koka's core is deliberately small — functions, a polymorphic type-and-effect system, ADTs, and effect handlers — and every function's row of effects is part of its type, so pure and effectful code are distinguishable at a glance ([Koka book](https://koka-lang.github.io/koka/doc/book.html), [MSR project page](https://www.microsoft.com/en-us/research/project/koka/)). Its compilation strategy, Perceus, does garbage-free reference counting with in-place reuse analysis, reaching within ~10% of C++ on tree-manipulation benchmarks with no tracing GC or runtime at all ([Perceus paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2020/11/perceus-tr-v1.pdf), [PLDI 2021](https://dl.acm.org/doi/10.1145/3453483.3454032)). This is directly relevant to Agel: Koka demonstrates that "first-class effects, statically tracked" and "no tracing GC" are not in tension — a fully effect-typed language can still compile to a single-pass RC-with-reuse backend, which is exactly the kind of backend Agel's from-Agel x86-64 emitter would need if it ever handles non-integer, heap-allocated data.

**Unison.** Unison hashes every definition by its normalized AST, so code is identified and stored by content rather than by name; there is no "build" step, dependencies resolve by hash, and Unison hit a 1.0 release on content-addressed code in November 2025 ([Unison big idea](https://www.unison-lang.org/docs/the-big-idea/), [1.0 announcement coverage](https://byteiota.com/unison-1-0-content-addressed-code-hits-production/)). Its `Remote` ability lets a function say where it executes; missing dependent code is shipped to the remote node automatically ([HN discussion](https://news.ycombinator.com/item?id=33638045)). For an agent-authored language this matters twice over: (a) content addressing gives a natural, collision-proof way to memoize and cache LLM-generated code and to detect when a model regenerated a semantically identical function it should have reused; (b) it removes an entire class of "the agent edited the wrong copy" and dependency-drift bugs that plague long agent sessions. Agel already has a "canonical encoding of state" and digests; extending that same content-addressing discipline to *code* (not just world state) would let Agel deduplicate and diff agent-written definitions the way Unison does.

**Bend / HVM (Higher Order Company).** Bend compiles a Python-flavored surface language to HVM2, a massively parallel interaction-combinator evaluator; because data is immutable, independent reductions run in parallel with no locks, "scaling like CUDA" for tree- and graph-shaped workloads ([Bend GUIDE.md](https://github.com/HigherOrderCO/bend/blob/main/GUIDE.md), [How Bend Works](https://towardsdatascience.com/how-bend-works-a-parallel-programming-language-that-feels-like-python-but-scales-like-cuda-48be5bf0fc2c/)). This validates Agel's immutable-values choice as a parallelism enabler, though Agel's tree-walking, no-TCO, depth-256 evaluator is nowhere near exploiting it yet — worth flagging as a long-run opportunity once/if Agel needs to fan out agent computation rather than run it turn-by-turn.

**Mojo, Lean 4, Rust-as-target.** Lean 4 is itself self-hosted (a reimplementation of Lean in Lean), compiles to C, and — notably for Agel's "compiled backend written in the language itself" ambition — has a from-scratch verifier written in Lean that runs only 20–50% slower than the original C++ one while checking all of mathlib ([Lean 4 system description](https://lean-lang.org/papers/lean4.pdf)). Its memory model is exactly Koka's Perceus RC-with-reuse, again reinforcing that "small effectful/functional core + Perceus-style RC" is a validated pattern for a self-hosted, GC-runtime-free language — a strong signal for what an eventual heap-allocated Agel-in-Agel evaluator should use instead of full tracing GC. Rust as an LLM target is well attested empirically (strict borrow checker catches whole bug classes the model would otherwise leave in), but is not itself agent-native: no transactions, no capabilities-as-language-feature, effects are ad hoc (`Result`, panics, unsafe).

**WebAssembly component model / WASI.** WASI's model — zero ambient authority, the host grants file/socket/clock access explicitly, components interact only through typed imports/exports (WIT) with no shared memory — is a mature, standardized instance of exactly the capability discipline Agel wants for its host words ([WASI security](https://wasi.dev/security), [component model status](https://eunomia.dev/blog/2025/02/16/wasi-and-the-webassembly-component-model-current-status/)). Agel's "capabilities the evaluator checks before an effect word runs" is philosophically identical to WASI's capability-per-import model; the concrete lesson to borrow is WIT-style typed interfaces for host words, so a capability isn't just "you may call `net:connect`" but carries a statically-checked shape.

**CapTP / E / Spritely Goblins — the closest relative.** This is worth dwelling on because it is *very* close to Agel's model. Goblins gives each "vat" an actormap — a transactional heap for object communication that supports rollback and time-travel: "changes happen within a transaction, and if an unhandled exception occurs, history can be rolled back as if the message never happened" ([What is Goblins?](https://files.spritely.institute/docs/guile-goblins/0.10/What-is-Goblins_003f.html), [High-level view](https://files.spritely.institute/docs/guile-goblins/0.14.0/High-level-view.html)). Objects are capabilities; a remote peer can only use capabilities explicitly handed to it, enforced through CapTP over OCapN, which also gives promise pipelining and distributed GC ([CapTP docs](https://files.spritely.institute/docs/guile-goblins/0.13.0/CapTP-The-Capability-Transport-Protocol.html), [OCapN](https://files.spritely.institute/docs/guile-goblins/0.10/OCapN-The-Object-Capabilities-Network.html)). Agel's "transactional worlds (commit/rollback per form and per agent turn)" is structurally Goblins' actormap turn model, and Agel's evaluator-checked capabilities are structurally CapTP's object capabilities — but Goblins additionally gives capabilities *network transparency* (promise pipelining so a capability received from a remote peer can be invoked before the network round-trip completes) and *distributed* garbage collection of capabilities. Agel currently has capabilities and worlds within a single kernel/process; it doesn't yet have a distributed capability-passing protocol between agents on different machines. If DOOM-agent-style multi-agent scenarios ever span machines, CapTP/OCapN is the concrete protocol to study or adopt rather than reinvent.

**Erlang/Gleam, Datalog/Datomic.** Erlang's supervision trees are the direct ancestor of "agents with isolated heaps/mailboxes/typed protocols/supervision" — Agel already has this lineage; Gleam adds a static type system on the BEAM, suggesting Agel's dynamically-typed-with-conditions core could grow an optional static layer without abandoning the actor model. Datomic's model — an immutable, append-only set of time-stamped facts ("datoms"), queried with Datalog, with full "as of" time travel and strong transaction ordering ([Datomic overview](https://docs.datomic.com/datomic-overview.html), [Wikipedia](https://en.wikipedia.org/wiki/Datomic)) — is essentially what a "claims/facts store" for Agel agents would look like: instead of agents mutating shared state, they assert immutable, timestamped facts that other agents (and future replay/debugging tools) can query as-of any point. This maps cleanly onto Agel's existing "canonical encoding of state (digests, world files, deltas)" — the missing piece is a query layer (Datalog-like) over that history, not just snapshot/diff.

**LLM-code-generation-friendliness literature.** Direct research on "make languages easier for LLMs" is thin but converges on a few points worth taking seriously: (1) uniform syntax matters because LLMs (especially when multiple agents or turns touch the same code) struggle with inconsistent style, so a language with almost no syntax (Agel's Lisp core) removes a whole failure axis ([survey on low-resource/DSL code-gen](https://arxiv.org/pdf/2410.03981)); (2) giving the model a compiler/typechecker in the loop to catch syntax/type/semantic errors as it goes measurably improves success rates — "using a compiler to perform static analysis on code generated so far can detect simple syntactic errors, type errors, and deeper semantic errors such as non-terminating loops" ([feedback from testing and static analysis](https://arxiv.org/html/2412.14841v1)); (3) "Statically Contextualizing LLMs with Typed Holes" explores feeding the model live type/scope information at the exact point it's generating, i.e. structural/incremental compilation as a first-class dialogue partner rather than a batch step ([typed holes paper](https://arxiv.org/pdf/2409.00921)); (4) execution-based feedback (tests, REPLs) remains the most reliable signal for iterative refinement ([survey](https://arxiv.org/pdf/2410.03981)). Agel's fuel-bounded, deterministic, replayable evaluation is unusually well-suited to this: a REPL-in-the-loop for an agent is only trustworthy if re-running the same form twice gives the same answer, which Agel already guarantees by design.

### What's validated vs. missing

**Validated by this survey:**
- Small orthogonal core + "everything else is a call" (matches Koka, Lean 4, Unison's minimalism, and the LLM-friendliness literature's uniform-syntax finding).
- Immutable values (matches Bend/HVM's parallelism story and Goblins/Datomic's transactional-history story).
- Transactional commit/rollback per turn (matches Verse's `<transacts>` and Goblins' actormap almost exactly).
- Capabilities checked by the evaluator before effects (matches WASI's zero-ambient-authority model and CapTP's object capabilities).
- Deterministic fuel budgets + a model-effect journal for replay (nothing else surveyed has this baked in this cleanly for *LLM* calls specifically — this is a genuine Agel differentiator worth documenting as such, not just an internal detail).

**Missing, in priority order suggested by the survey:**
1. **First-class, statically-tracked effects instead of "host words."** Koka and Verse both show effects can be types, not just runtime capability checks. Agel checks capabilities dynamically before an effect word runs; it does not yet let a function's *type* say "this may fail," "this may call the model," "this touches the filesystem." A typed-effect row (even a minimal one, à la Koka) would let an agent's own reasoning — and any static checker — see the effect surface of code before running it, not just at the moment of the call.
2. **A claims/facts store with time, à la Datomic.** Agel has world files, deltas, and digests but (per the description given) no Datalog-like query layer over historical facts. For multi-agent supervision and debugging, "what did agent X assert about Y as of turn N" is a natural query that the current snapshot/diff model doesn't answer directly.
3. **Structured concurrency for agents.** Erlang-style supervision gives failure isolation; it does not by itself give the "wait for all children, propagate cancellation" discipline of structured concurrency (Kotlin coroutines, Trio). Given agents already have supervision, adding scoped-lifetime concurrency (a child agent cannot outlive its spawning form/turn unless explicitly detached) would close a real gap between "isolated and supervised" and "cannot leak."
4. **Distributed capability passing (CapTP/OCapN-style).** Needed only when agents cross machine boundaries, but worth designing now rather than retrofitting, since Agel's capability model is otherwise a perfect fit.
5. **Types/contracts for agent protocols.** "Typed protocols" are named in Agel's own description but the survey (Gleam on BEAM, Verse's `<decides>`) suggests concretely what "typed" should mean: session-type-like protocols where a mailbox's expected message sequence is statically checked, not just its message shape.
6. **Time-travel debugging as a first-class tool, not just a replay mechanism.** Goblins gets time-travel "for free" from its transactional actormap; Agel's per-turn commit/rollback plus model-effect journal already contains everything needed — what's missing is tooling (a debugger that can step backward through committed turns) rather than a new mechanism.

## Part 2 — How Rust helps, and where the Rust/Agel boundary should sit

Rust's role across serious language/OS substrates is remarkably consistent: **Rust owns the trusted computing base — hardware contact, memory-safety-critical isolation, and performance-critical codegen — while the higher-level language or policy layer is pushed as far up the stack as the substrate allows.**

- **no_std runtimes and MMTk.** MMTk is a Rust memory-management toolkit — allocators, "spaces" (policies for memory regions), and work packets composed into pluggable GC "plans" (NoGC, MarkSweep, MarkCompact, etc.) — used as a pluggable backend by JikesRVM, PyPy's RPython-generated runtimes, and other VMs ([MMTk docs](https://docs.rs/mmtk/latest/mmtk/), [MMTk status](https://www.mmtk.io/status)). This is a template for Agel's own hosted runtime: rather than writing a bespoke GC by hand if/when Agel's heap grows beyond RC-with-reuse's sweet spot, bind `agel-core` to MMTk the way JikesRVM and PyPy did, keeping GC engineering in a well-tested Rust crate while policy (which plan, when to collect) stays configurable.
- **Cranelift and wasmtime.** Cranelift began as wasmtime's JIT backend, is now general enough to be an optional Rust nightly codegen backend for debug builds, compiles roughly an order of magnitude faster than LLVM-based WAVM, and is production-hardened purely through Wasmtime's usage ([Cranelift in Rust nightly](https://lwn.net/Articles/964735/), [Cranelift README](https://github.com/bytecodealliance/wasmtime/blob/main/cranelift/README.md)). Agel's description already includes "a Cranelift JIT on the host" — this is the right call precisely because Cranelift is designed for fast, simple, correctness-first codegen rather than maximal optimization, which matches a research language's iteration speed needs better than LLVM would.
- **Theseus OS — "intralingual design."** Theseus pushes OS invariants (resource ownership, exclusive access, cleanup ordering) into Rust's affine type system via typestate, explicitly trying to "close the semantic gap between compiler and hardware" so the compiler — not runtime checks — enforces correctness ([Theseus GitHub](https://github.com/theseus-os/Theseus), [OSDI '20 paper](https://www.usenix.org/system/files/osdi20-boos.pdf)). The direct lesson for Agel: wherever Agel's Rust kernel currently enforces an invariant with a runtime check (a capability lookup, a protection-domain boundary), ask whether Rust's own type system (typestate, phantom types, ownership) can make the invalid state unrepresentable instead — cheaper at runtime and provable at compile time.
- **Hubris and Tock — minimal, capability/isolation-first kernels.** Hubris is ~2000 lines of Rust, does scheduling/isolation/IPC only, and treats every driver as an unprivileged, independently-restartable task ([Hubris reference](https://hubris.oxide.computer/reference/), [Hubris GitHub](https://github.com/oxidecomputer/hubris)). Tock uses "capsules" — a language-based (not hardware-based) isolation abstraction inside the kernel with zero runtime overhead, layered under hardware MPU isolation for actual untrusted user processes ([Tock design](https://www.tockos.org/documentation/design/)). Agel's microkernel (drivers, filesystem, evaluator, processes all unprivileged) is already Hubris-shaped; Tock's capsule idea suggests a cheap intermediate isolation tier for trusted-but-separable *kernel-internal* Rust modules, distinct from the hardware-enforced isolation used for full processes — useful if Agel ever wants to isolate, say, the digest/canonicalization code from the scheduler without paying a full protection-domain crossing.
- **rustc's own bootstrap.** rustc is written in Rust and compiled by a previous rustc (stage0 pulled from a prior release), which is the same "N-1 builds N" pattern Agel will eventually need for its own backend; nothing exotic here, but it's evidence the pattern scales to a large, real compiler.

**What Agel should keep in Rust permanently:** hardware bring-up (boot, interrupt/exception vectors, MMU/page-table setup), the microkernel's protection-domain enforcement and IPC primitives, the ELF loader, and any GC/allocator machinery adopted from MMTk. These are exactly the pieces where a memory-safety bug is a security bug and where Rust's ownership model earns its keep with no runtime cost — the Theseus thesis.

**What can migrate to Agel-emitted code over time:** the hosted runtime's evaluator loop itself (already the plan — self-hosting the evaluator), the standard library, the compiler frontend (already done: reader, macro expander, IR compiler run in Agel in the OS), and eventually parts of the backend beyond the current integer subset. The x86-64 backend written in Agel is the leading edge of this migration and should keep growing before touching the kernel's Rust core.

## Part 3 — Crossing the next self-hosting line

Agel already has a frontend and an integer-only backend running *inside* the OS, emitting ELF images the OS installs and runs. The next line to cross is writing the evaluator/runtime itself — not just user programs — in Agel. History gives a fairly consistent playbook.

- **Squeak's Slang.** Slang is not a separate language but a *restricted subset of Smalltalk* — no real message sends, no full objects, methods map onto C functions, instance variables map onto C globals — mechanically translated to C so the VM can be written, debugged, and instrumented inside the live Smalltalk environment and still get real execution speed ([Squeak Slang wiki](https://wiki.squeak.org/squeak/2211), [transpiling Slang paper](https://www.hpi.uni-potsdam.de/hirschfeld/publications/media/BraunTaeumelMirandaHirschfeld_2023_TranspilingSlangMethodsToCFunctionsAnExampleOfStaticPolymorphismForSmalltalkVmObjects_AcmDL.pdf)). This is the closest precedent to "Agel Slang": a subset chosen not for expressiveness but for *mechanical translatability*, developed and debugged inside the full high-level environment before being compiled down.
- **Jikes RVM.** A metacircular JVM written in Java, bootstrapped by an existing "host" JVM that runs a boot-image writer: the writer uses reflection to build a byte-image of all the objects the new VM needs, and a small C loader boots that image at runtime; garbage collection is delegated to MMTk ([Jikes RVM overview](https://en.wikipedia.org/wiki/Jikes_RVM), [boot image layout](https://www.researchgate.net/publication/228982139_Boot_Image_Layout_for_Jikes_RVM)). The pattern — host runtime builds a frozen image of the target runtime's initial heap, a minimal native loader boots it — maps directly onto how Agel could bootstrap an Agel-in-Agel evaluator: use the existing Rust-hosted `agel-core` to build and freeze the initial heap/state of the Agel-Slang evaluator, then have a minimal Rust loader (already present as the kernel/loader) bring it up.
- **PyPy/RPython.** RPython is Python restricted enough that type inference and translation to C (or other backends) become tractable; PyPy's actual payoff is that its meta-tracing JIT is generated *from* the RPython interpreter definition, not hand-written, so the same technique applies to any interpreter written in RPython, not just Python's ([RPython FAQ](https://rpython.readthedocs.io/en/latest/faq.html), [PyPy architecture chapter](https://aosabook.org/en/v2/pypy.html)). The lesson for Agel: define "Agel Slang" precisely enough that a JIT or native compiler can be *derived* mechanically from the interpreter's own structure, rather than hand-writing a second, divergent fast-path implementation — one interpreter, one source of truth, two compilation targets (tree-walk for the hosted runtime, compiled ELF/JIT for the native path).
- **Chez Scheme / Racket CS.** Chez is self-hosting: a small C kernel loads "boot files" — pre-compiled object code for the parts of the system written in Scheme itself — and Racket CS bootstraps Chez by re-implementing just enough of Chez in Racket to load Chez's compiler *from source* and apply that compiler to itself ("cs-bootstrap"), which is precisely how a from-scratch chain avoids needing a binary blob forever ([bootstrap doc](https://docs.racket-lang.org/racket-build-guide/bootstrap.html), [cs-bootstrap package](https://pkgs.racket-lang.org/package/cs-bootstrap)). This "the new host reimplements just enough of the old host to load the old host's compiler from source" trick is the concrete recipe for avoiding a permanent hand-off point in Agel's own bootstrap chain: rather than freezing a binary boot image forever, keep a from-source path where a minimal Rust (or hosted-Agel) shim can load and run the Agel-Slang compiler's *source*.
- **Klein (Self VM in Self).** Klein is a metacircular Self VM written entirely in Self, bootstrapped by "snapshotting" a live Self image into a byte-array bootstrap image containing objects, meta-objects, and statically compiled machine code — blurring the line between "the VM" and "an application running on the VM" almost completely ([metacircular VM paper](https://www.researchgate.net/publication/200040544_Constructing_a_Metacircular_Virtual_Machine_in_an_Exploratory_Programming_Environment), [Klein GitHub](https://github.com/AdamSpitz/klein)). Klein is the most aggressive point on this spectrum (VM and application are the same live image) — probably further than Agel needs to go, but it's useful as the far end of the design space when deciding how much of the kernel's Rust core to eventually dissolve into Agel-in-Agel.
- **"Trusting trust" and diverse double-compiling.** Ken Thompson showed a compiler can insert a backdoor into everything it compiles, including its own next generation, such that inspecting source code alone can never detect it. David Wheeler's Diverse Double-Compiling counters this by compiling the suspect source with a *second, independent* compiler, then recompiling the *result of the first compiler* with that second compiler, and checking the two outputs match byte-for-byte — catching the attack without needing to trust either compiler's provenance ([DDC dissertation](https://dwheeler.com/trusting-trust/dissertation/html/wheeler-trusting-trust-ddc.html), [Reflections on Trusting Trust retrospective](https://paperswelove.org/papers/reflections-on-trusting-trust-8671ec46/)). Agel's own description already says it does "diverse comparison of host vs guest toolchain output" — that is DDC's exact structure, and it should be treated as a permanent, load-bearing test in CI (byte-equal output between the Rust-hosted pipeline and the Agel-in-the-OS pipeline for every stage that exists in both), not a one-off validation.

### Concretely: an "Agel Slang"

Following the Slang/RPython precedent, an Agel Slang subset for writing the evaluator/runtime in Agel needs at minimum:
- **A fixed-shape heap model** — tagged cells/records with a small, closed set of shapes (cons cells, vectors/records, closures, symbols/interned texts) so a mechanical translator can lay them out without general-purpose dynamic dispatch.
- **Lists and texts with known, bounded representations** — not full arbitrary-precision/streaming abstractions, mirroring how Slang restricts Smalltalk collections to what maps onto C arrays.
- **Tail calls** — Agel's current hosted runtime explicitly has *no* TCO and a call depth of 256; an evaluator written in Agel-Slang to run the evaluator loop itself needs guaranteed TCO (or an explicit trampoline construct as a Slang primitive) since "the interpreter's own dispatch loop recurses" is exactly the shape that blows a depth-256 budget instantly.
- **Explicit GC roots** — a Slang-level primitive to declare "this local is a root," matching how Slang/RPython/Jikes all need the translator to know statically what the collector must trace, since a restricted subset can't rely on full reflection over an arbitrary call stack.
- **No dynamic macro use inside Slang itself** — macroexpansion happens at the meta-level (in full Agel, ahead of time), producing plain Slang forms; Slang itself should not need `defmacro`/`macroexpand-1` at runtime, mirroring RPython's restriction against runtime type-shape changes.

### A proposed bootstrapping order with proofs

1. **Freeze "Agel Slang" as a named, versioned subset** (grammar + the primitives above) with a conformance checker written in today's Rust-hosted `agel-core`. *Proof:* the checker rejects a fixed adversarial corpus of non-Slang forms and accepts a fixed corpus of valid ones — a golden-file test, not a judgment call.
2. **Write a minimal Agel-Slang evaluator loop (eval/apply core, no stdlib) in Agel-Slang**, run it *interpreted* inside the existing hosted `agel-core` (Slang-in-full-Agel, tree-walked) to validate semantics before any compilation exists. *Proof:* this Slang-interpreted-in-Rust-hosted-Agel evaluator produces byte-identical digests, on a fixed test-form corpus, to the existing Rust `agel-core` evaluator.
3. **Compile the Agel-Slang evaluator with the existing Agel-in-the-OS backend** (extending the integer-subset x86-64 backend enough to cover Slang's heap model — cons cells, closures, tail calls) to an ELF image. *Proof:* run that ELF's evaluator against the same fixed test-form corpus and require byte-identical output/digests against both (a) the Rust `agel-core` reference and (b) step 2's Slang-in-Rust-hosted-Agel run — a three-way, not just two-way, comparison.
4. **Boot-image the result, Jikes-style**: have the current Rust-hosted runtime snapshot the compiled Agel-Slang evaluator's initial heap state into a world file, and have the microkernel's existing loader (already loading ELF images) boot that image directly, without going through the Rust-hosted `agel-core` at process-start. *Proof:* the OS can start a session using only the compiled-Agel-Slang evaluator and the kernel loader — zero Rust `agel-core` invocations in that boot path — while a parallel CI job still runs the three-way digest comparison from step 3 on every commit, so the frozen image is never trusted blindly (this is the Racket CS lesson: never let the from-source path atrophy behind a binary boot file).
5. **Extend Agel-Slang's backend coverage from the integer subset toward the full heap model** (cons cells, closures, vectors, tail calls) incrementally, each extension gated by the same three-way byte-equality proof from step 3, so "the backend now handles closures" is never asserted without a diff-free comparison against the Rust reference.
6. **Only after 1–5 are stable**, consider migrating standard-library pieces and eventually the macro expander/IR compiler's *own* runtime dependencies from being merely "run in Agel" (today) to being "written in Agel-Slang and self-compiled" (Klein/Chez-style), keeping the DDC-style diverse comparison against the Rust toolchain as a permanent CI gate rather than a one-time migration check.

## Recommendations for Agel (prioritized roadmap)

1. **[Language, near-term, bounded]** Add a minimal statically-tracked effect annotation to host words (Koka/Verse-inspired) — even just a closed enum of effect classes (`:io`, `:model`, `:mutate-world`) attached to each host word's declared signature. *Proof:* a checker that walks a call graph and flags any effect word invoked without the enclosing form declaring that effect class; runs as a CI lint over the existing stdlib with zero false positives on current code.
2. **[Language, near-term]** Prototype a Datalog-style query layer over existing world-file deltas/digests (Datomic-inspired), answering "what facts existed as of turn N" without new storage — pure read-side addition. *Proof:* three canned queries (state at turn N, diff between two turns, first turn a given fact appeared) return correct results against a fixed multi-turn world-file fixture.
3. **[Language, medium-term]** Content-address Agel *code* the way Unison does — hash normalized ASTs of top-level defs, dedupe identical agent-authored definitions, and use the hash (not the name) as the identity macroexpansion/linking key internally. *Proof:* two independently-written, alpha-equivalent function bodies collapse to one stored definition in a test corpus; a renamed-but-unchanged function keeps its hash.
4. **[Language, medium-term]** Structured-concurrency scoping for agent spawn (child agent lifetime bound to spawning form/turn unless explicitly detached). *Proof:* a test agent that spawns a child and rolls back its turn also tears down the child, with no orphaned mailbox left in the world state.
5. **[Rust/Agel boundary, near-term]** Formalize the Rust-permanent set explicitly in docs: hardware bring-up, MMU, protection-domain enforcement/IPC, ELF loader, any adopted MMTk bindings. *Proof:* a CI check (e.g., a path allowlist) that fails if new Rust code is added to the kernel crate outside that declared set without an explicit exception label.
6. **[Rust/Agel boundary, medium-term]** Evaluate MMTk as the GC backend once/if Agel-Slang needs heap objects beyond what Perceus-style RC-with-reuse handles well; until then, prefer Koka/Lean-style RC+reuse to avoid a tracing GC dependency at all. *Proof:* a microbenchmark corpus (cons-heavy, closure-heavy) where RC+reuse throughput stays within an agreed factor (e.g. 3x) of the Rust-hosted baseline before MMTk is considered necessary.
7. **[Self-hosting, near-term, bounded]** Freeze "Agel Slang v0" (grammar + conformance checker) per step 1 of Part 3. *Proof:* golden-file accept/reject corpus, versioned and checked into the repo.
8. **[Self-hosting, medium-term]** Implement and validate the Agel-Slang evaluator loop per steps 2–3, with the three-way byte-equality digest proof as the CI gate, extending the existing "diverse comparison of host vs guest toolchain output" practice from compiled programs to the evaluator itself.
9. **[Self-hosting, medium-term]** Boot-image the compiled Agel-Slang evaluator per step 4, keeping the from-source path (Rust `agel-core` building the image) as a permanently-run CI job, never a one-time migration — this is the Racket CS "don't lose the from-source bootstrap" lesson applied directly.
10. **[Self-hosting, long-term]** Incrementally extend backend coverage (closures, vectors, tail calls) per step 5, then consider migrating stdlib/macro-expander internals to Agel-Slang per step 6, always gated by the same byte-equality discipline — treating "does the guest-compiled toolchain byte-match the host-compiled one" as Agel's permanent trusting-trust defense, exactly as Wheeler's DDC intends.
